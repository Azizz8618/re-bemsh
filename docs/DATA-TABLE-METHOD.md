### 3.0 ВХОД И ВЫХОД

ВХОД [Д/структура]: сегментированный массив, полученный в
фазе 2. Это список непересекающихся пробегов адресов
(зона.слово starting..ending) с пометкой "плотный /
непустой / конд", уже отделённый от кода и забела.
Каждый сегмент = упорядоченный набор 48-битных слов:

  сегмент := { зона, addr0, addr1, word[i] }, i=0..N-1

Фаза 2 уже дала (пример, SERVICE-TABLES-B2.md:32-83):
  540:465-527   35  KOI7+код    -> мнемоники
  553:55-74     16  Э70|зп 0     -> dispatch
  556:114-1777 948  944 нуля     -> FILL+указ.
  570:3-67      53  зпМ17|пб N  -> дескрипторы

ВЫХОД фазы 3: для каждого сегмента вердикт из 6 классов
(§3.2e) с перечислением требований к доказательствам
(§3.3) и честных [Г]-оговорок. Фаза 3 НЕ восстанавливает
исходник транслятора.

Ограничение входа [Д]: "конд" из disbesm6 - НЕ доказа-
тельство данных и НЕ доказательство кода. Данные тоже
декодируются в opcode (SERVICE-TABLE-0156.md:15-18;
SERVICE-TABLES-B-OTHER.md §1.5). Требуется двойная
проверка: байты gold + forced-листинг.

### 3.1 АЛГОРИТМ ДЕКОДИРОВАНИЯ (шаги a-f)

#### 3.1a. Расщепление 48 бит и разбор полей [Д]

Для каждого слова:
  L = word >> 24        (старшие 24 бита)
  R = word & 0xffffff   (младшие 24 бита)

L и R подаются в re-siprod/tools/siprod_asm.py:100 decode.
Возвращаемые поля (siprod_asm.py:102-117):
  name   - мнемоника из таблицы OPS (или illegal)
  reg    - номер регистра (half >> 20) & 0xF, т.е. М0..М17
  op     - код операции (1-я структура: биты 18..15,
           2-я структура: биты 17..12)
  addr   - поле адреса (1-я: 15 бит, 2-я: 12 бит +
           EXP-расширение до 0o700000)
  struct - 1 = первая структура (с регистром)
  dms    - бит 0x200000, признак DMS-перемещаемости
  exp    - бит 0x40000, признак расширения адреса

Правило [Д]: reg/KOP/addr/dms/exp - структурные факты.
Смысл поля - [Г], пока не найден читающий код.
Пример (Z0172-STRUCTURE.md:24):
  L=`2240IIII` = уиа М4, addr=IIII  (ID)
  R=`0300TTTT` = пб М0, addr=TTTT  (TARGET)
Мнемоника "уиа"/"пб" здесь - просто форма битов, не
исполнение: в 0172 CALL=0 и штампа нет (:97).

#### 3.1b. Четыре кодировки; как отличить текст от числа [Д]

Таблицы dtran.cc:
  GOST-8   dtran.cc:167 gost_to_utf[0x00..0x7F]
  6-бит TEXT dtran.cc:183 text_to_utf[0..63]
  ITM      dtran.cc:195 gost_to_itm / itm_to_utf
  KOI-7    таблица besmtool view --encoding=k
             (docs/TEXT-CONSTANTS.md §3, колонка 26:38)

Практический вызов (docs/TEXT-CONSTANTS.md:85):
  besmtool view 2348 --start=<ЗОНА> --length=1 \
    --encoding=g,k,t,i
Печает 2 слова в строке, 4 колонки G|K|T|I по 12 символов;
чётное слово = первые 6, нечётное = вторые 6 знаков
(:89-91).

ПОСЛЕДОВАТЕЛЬНОСТЬ проверки (TEXT-CONSTANTS.md §2):
  1. disbesm6 "п'...'" - НЕ доказательство текста. Это лишь
     прохождение is_good_gost (disbesm6.c:531):
       байт < 0x10 ИЛИ 0x20 <= байт <= 0x4D.
     Пример-ловушка: 0140.0044 = `2000000002200000` байты
     40 00 00 09 00 00 -> "п'F00900'", но это ЧИСЛО
     (:61-65).
  2. dtran is_valid_gost / is_likely_gost (dtran.cc:502,
     519) - байты < 0x116, плюс "запрещённые" 020/021/024/
     034; is_likely требует (word>>40) или >2 знаков.
  3. dtran is_likely_text (dtran.cc:454-476) для 6-бит:
     нет "дыр" в середине, >1 знака; ВНИМАНИЕ: все 64 кода
     TEXT печатные, поэтому 734/817 слов 0172 дают "текст"
     - артефакт таблицы (Z0172-STRUCTURE.md:82-84).
  4. KOI-7 читается у таблицы мнемоник 0137/0540, там же
     GOST-колонка - мусор (TEXT-CONSTANTS.md:93-96, §6.1).
  5. Итоговый признак текста [Д]: РЯД из >=3 соседних слов
     с осмысленными словами + besmtool search '<фраза>' ->
     зона.слово (:69-76). Одиночные 'F'/'N' - не текст.

Вывод [Д]: в 0172/0156/0153/основных числовых пулах фраз
НЕТ (Z0172-STRUCTURE.md:86; SERVICE-TABLE-0156.md:80-81;

#### 3.1c. VARYING vs CONSTANT по записям (метод 0172) [Д]

Цель: различать поле-индекс (ID) и поле-указатель (TARGET)
внутри однородной группы слов.

Алгоритм:
  1. Сгруппировать слова сегмента по постоянному полю
     (например, по R-половине или по байтам 3-5).
  2. Внутри группы посчитать, какой байт/поле меняется,
     а какой инвариантен.
  3. Меняющееся поле = ID/индекс; константное = TARGET/tag.

Образец (Z0172-STRUCTURE.md:29-44) [Д]:
  TARGET a3010: 0774-1001 (8 записей),
    ID 0012 0014 0030 0016 0020 0022 0026 0136
  TARGET a3656: 1642-1655 (12 записей)
  TARGET a3676: 1660-1675 (14 записей)
  Байтовая проверка: 0172.1642 `4a004e0c07ae` vs
  1645 `4a003a0c07ae` - отличается ТОЛЬКО байт 2 (ID);
  байты 3-5 (`0c07ae` = 03003656) постоянны.
  1660 vs 1663: снова только байт 2; `0c07be`=03003676.
[Г] F = ID -> адрес обработчика (диспетчеризация): ID растут
с шагом 2, несколько ID отображаются в один TARGET (:45-47).

ЗЕРКАЛО 0165/0170 [Д] (там же :51-60):
  0165.0367 `0900000c0591` (02200000|03002621)
  0165.0370 `0900000c067c` - меняются байты 4-5 (указатель)
  0170.0003 `5c84380c062d` (27102070|03003055)
  0170.0006 `5c84380c056c` - меняются байты 4-5
Итого: 0165/0170 = [константный тег | переменный адрес],
а 0172 = [переменный ID | константный адрес]. Оба из
семейства [поле | указатель], но 0172 инвертировано [Г].

## 4. ФАЗА 4: ПОИСК ЧИТАТЕЛЯ

Раздел собран из analysis/DATA-TABLE-METHOD-STAGE4.md
(внутренняя нумерация 2a-2e, 3-7 сохранена для ссылок).

### 4.0 НАЗНАЧЕНИЕ ЭТАПА

Этап 3 отвечает ЧТО лежит в таблице (класс, структура,
границы). Этап 4 отвечает КТО её читает.

Читатель - это код (команда или процедура), который берёт
слово таблицы как операнд и использует как данные:
индекс, код, указатель, маску. Цель этапа - для каждой
классифицированной таблицы получить один из трёх вердиктов:

* FOUND - читатель доказан статически и/или динамически;
* NONE FOUND - читателя нет ни в одном доступном источнике;
* FALSE POSITIVE - "читатель" найден, но это не читатель.

Важное различие (NUMERIC-ARRAYS-B1.md §1, §6): структура и
адреса - [Д], а смысл полей остаётся [Г], даже когда
читатель найден. Нахождение читателя не равнозначно
пониманию семантики.

### 4.1 ВХОД ЭТАПА 4

Входом служит результат Этапа 3: классифицированный массив с
точно известным диапазоном. Минимальный набор полей:

| поле | содержание | пример |
|---|---|---|
| зона-носитель | номер зоны тома 2048/2348 | 0172, 0144 |
| диапазон | слово-начало .. слово-конец | 0260-1740 |
| физич. база | адрес страницы (если известен) | 040000₈ |
| класс | DESCR/CONST/GLYPH/NAME/POINTER/... | OPCODE |
| гипотеза | ожидаемая роль таблицы [Г] | код->графема |

Примеры входа (оба - [Д]):

* `0172.0260-1740`, класс не определён, база неизвестна
  (Z0172-READER.md:10-14);
* `0144.0426-0437`, 10 слов, класс OPCODE, база `040000₈`
  (NUMERIC-ARRAYS-B1.md:83-90).

Если класс таблицы уже указывает на reader (например,
DESCR из 0140 читается коротким загрузчиком), Этап 4 всё
равно проверяет ссылку независимо: класс - [Г],
ссылка - [Д].

### 4.2 АЛГОРИТМ ПОИСКА ЧИТАТЕЛЯ

Порядок шагов фиксирован: от дешёвой статики к дорогой
динамике. Каждый шаг записывает verdict + file:line.

#### 4.2a. ШАГ 4a. СТАТИКА: ПРЯМЫЕ ОПЕРАНДЫ

Цель: найти команду, чей числовой операнд попадает в
диапазон таблицы.

1. Искать по всем `bemsh/*.be` (69 файлов) и всем
   `dis-forced/Z<зона>.asm`: УИА, СЧ, ЗП, МОДА, ПБ, ПВ,
   НТЖ, И, ПИО, ПИНО, СЧИ, СЧМ с операндом в регионе.
2. Учесть физическую базу. Зона грузится на страницу
   `N * 02000₈` (MEMORY-MAP.md §3: `extra.c:1914-1916`),
   поэтому в ОП операнд равен `база + смещение`, а не
   локальному номеру слова:
   * [Д] `уиа '40426'(М11)` в `dis-forced/Z0144.asm:1846`
     = `040000₈ + 0426` = зона 0144, слово 0426.
   * [Д] то же для '40446'..'40526' в [:1850-1856].
3. Локальный адрес НЕ есть ссылка на другую зону. В
   Z0172-READER.md:67-72 найдено 3959 вхождений операндов
   в регионе 0260-1740, но все - локальные адреса внутри
   своей зоны (например `ASM-Z0055.be:1158 НТЖ BR260`).

Команды:

```bash
grep -nE "'0?40426'|'40446'" dis-forced/Z0144.asm
grep -nE 'уиа|нтж|мода|сч' bemsh/MBE-Z*.be | grep -F '0426'
```

#### 4.2b. ШАГ 4b. КОСВЕННАЯ АДРЕСАЦИЯ

Прямой поиск пропускает читателя через регистр. Проверить:

1. Базовые регистры М13/М14/М16/М17 + смещение из
   диапазона. [Д] 452 вхождения в Z0172-READER.md:73-79,
   все внутри своей зоны:
   * `bemsh/MBE-Z0161.be:444 СЧ MB266(М14)`, база М14 =
     страница 0161 (`24000₈`, RAM-SNAPSHOT-MAP.md §3.4);
   * `bemsh/MBE-Z0152.be:1359 СЛИА MB0262(М13)`.
   Нет ни одного случая, где база загружена страницей
   искомой зоны и смещение попадает в таблицу [Д].
2. Косвенные переходы и мода: `ПБ(Мn)`, `ПВ(Мn)`,
   `МОДА`, `УПОТР`.
   * [Д] дескрипторы загрузчика: `нтж D00177-23(М7)`,
     `зп D00177-23(М7)` (`dis-forced/Z0140.asm:12,16`),
     база `мода '36436'` (`Z0142.asm:32`,
     NUMERIC-ARRAYS-B1.md:73-80).
   * [Д] `мода '36436'` как база поля 3 в 0143
     (`dis-forced/Z0143.asm:18-22`).
3. Проверка ИМЕНИ: совпадение цифр в метке ещё не ссылка.
   [Д] `C172 ЭКВ '172'` (`MBE-Z0144.be:618`) и
   `ПБ C172(М2)` (`:880`) - это МАЛЫЙ адрес 0o172, а не
   номер зоны 0172 (Z0172-READER.md:22-29).

Правило: смещение считается ссылкой на таблицу только при
доказательной загрузке базы нужной страницей (снимок или
`MEMORY-MAP.md §5`). Иначе это [Г], не [Д].

#### 4.2c. ШАГ 4c. ДЕСКРИПТОРНЫЕ УКАЗАТЕЛИ

Гипотеза: таблица может быть целью дескриптора другой зоны.
Процедура (Z0172-READER.md §2):

1. Найти дескрипторные массивы по характерным префиксам:
   * [Д] `022000000300` - 69 слов в `0165.0367+`

3. Проверить два условия попадания:

4. Результат для 0172 [Д]: диапазон указателей

Структура `[тег | указатель]` у 0165/0170 - [Г], но сам

### 4.3 ИНТЕРПРЕТАЦИЯ РЕЗУЛЬТАТОВ

#### 4.3.1 READER FOUND (определённо)

Условие: прямая ссылка в `dis-forced/*.asm` или `.be`
совпадает с `база+смещение` И (желательно) подтверждена
трассой. Пример - 0144:0426, `уиа '40426'(М11)`.

Оговорка: читатель доказывает ИСПОЛЬЗОВАНИЕ слов, но не
описание полей. Смысл остаётся [Г].

#### 4.3.2 NONE FOUND

Отсутствие читателя - не "мусор", а один из трёх сценариев
[Г] (Z0172-READER.md §8):

 1. НЕисполняемый оверлей: таблица грузится в другой фазе
    или задании, отсутствующем в трассе `0-0`.
 2. Данные загрузчика/Монитора: зоны 0137-0146 вытеснены до
    точки съёма (`RESIDENT-ZONES.md:212`), читатель может
    быть там.
 3. Заготовка "на вырост": в 12/77 таблица правилась
    (diff=316), значит кем-то использовалась, но не в этом
    прогоне.

Все три [Г] не подтверждены прямым кодом. Роль остаётся
ОТКРЫТОЙ. Практический вывод: таблицу нельзя привязать к
ОП и нельзя считать участником конвейера
МАКРОРЕДАКТОР -> МАКРОМАШИНА -> АРАП в этом задании [Д].

### 4.5 ЧЕСТНЫЕ ОГОВОРКИ ФАЗЫ 4

1. Трасса покрывает ОДНО задание `0-0` (минимальный листинг
   `ТЕСТ СТАРТ 1`). Другая фаза может загрузить те же
   страницы другими зонами (CALL-TRACE-RUNTIME.md §5).
2. 18 снимков - дискретные точки. Между ними возможны
   оверлеи, не попавшие ни в одну
   (RAM-SNAPSHOT-EXTRA.md §6).
3. Отсутствие доказательства НЕ есть доказательство
   отсутствия. NONE FOUND = "не найден в доступных
   источниках", а не "никогда не читался".
4. boot-дамп пуст; самая ранняя точка - 03651, когда
   транслятор уже загружен. Ранняя загрузка идёт в
   супервизоре (`supmode=0100000`), breakpoint маскируется
   до 15 бит и недостижим (RAM-SNAPSHOT-EXTRA.md §1).
5. `dispak` печатает адрес СЛОВА, а не полукоманды; левая и
   правая команды дают одинаковый `abpc` (CALL-TRACE §6).
6. L1-слово по физическому адресу часто помечено `конд` и
   расходится с исполненной мнемоникой. Вывод опирается на
   PC-последовательность, не на L1 (CALL-TRACE §6).
7. Имена из `*МЕТ*`/`*EXECUTE` - логические/памятные адреса.
   Физическими якорями служит только побайтовая сверка и
   текстовые штампы (`0147.1315` и др.). Не подставлять
   логический адрес как физический (AGENTS.md §3).
8. CALL через `(Мn)`, `выпр`, `'NNNNN'` статически не
   считается (ENTRY-POINTS.md §6.2): счётчики занижены.

Итог Фазы 4 для каждого массива - одна строка:
`зона.диапазон | вердикт | источник | уверенность [Д/Г]`.

## 5. ФАЗА 5: СРАВНЕНИЕ ВЕРСИЙ И АНАЛОГИИ

### 5.1 ВХОД ЭТАПА 5

На вход подаётся результат этапов 1-4 для одной зоны:

 1. МАССИВ - границы, размер, паттерн слова. Формат:
    зона, адрес начала/конца, n слов, префиксы полей.
    Пример: 0172.0260-1740, 812 слов, префикс 0220.
    [Д: NUMERIC-ARRAYS-B2.md §3.8]
 2. КЛАССИФИКАЦИЯ этапа 3/4 - один из:
    CONST/MASK, NAME/ATTRIBUTE, DESCR/PTR, FILL,
    CODE, TAG/TEXT, ALPHA, DISPATCH, TABLE?.
    [Д: NUMERIC-ARRAYS-B1.md §5; B2.md §5; B2A.md §6]
 3. РЕЗУЛЬТАТ ЧИТАТЕЛЯ этапа 4 - найден ли код,
    читающий массив (УИА/СЧ/ЗП/МОДА/пб/сд), есть ли
    индексный доступ (Мn) или сдвиг сд. Если читатель
    не найден, это фиксируется как факт, а не как
    доказательство отсутствия смысла.
    [Д: NUMERIC-ARRAYS-ASM.md §4; B2B.md §5.2]
 4. эталонные дампы B и B2 (по 6144 байт на зону),
    их размеры и md5 из manifest.sha256 / versions.md §1.

Выход этапа 5 - вердикт: переименование / перекодировка /
сдвиг текста / различие установки, плюс оценённый
аналог в re-dispak со ссылкой module.be:line.

### 5.2 АЛГОРИТМ СРАВНЕНИЯ ВЕРСИЙ

#### Шаг a. Карта зон B -> B2 и проверка дампов

 1. Для зоны B с номером Z (восьм.) counterpart в B2 -
    Z + 0400: 0140->0540, 0172->0572, 0177->0577.
    Соответствие найдено сдвигом склейки:
    02400 - 0400 = 01000 = 1024 слова = одна зона,
    то есть OLD 0540+j <-> NEW 0140+j, j=0..31.
    [Д: versions.md §4]
 2. NEW 0137 не имеет пары (логически 0537 пуста).
    [Д: versions.md §8.2; reloc.md §5]
 3. Проверить дампы: ровно 6144 байт = 1024 х 6;
    md5 склейки NEW 2f503f..., OLD a14315...;
    штампы 0147.1315 = ВЕР.06/78 и
    0547.1315 = ВАР.12/77. [Д: versions.md §1-2]
 4. Отнести зону к классу карты версий:
    I (идентична), L (загрузчик), S (сдвиг текста),
    C (правка кода/таблицы), M (смешанная).
    [Д: versions.md §5-6]
 5. Зоны 0137-0143 (класс L) из вывода о версии
    ИСКЛЮЧИТЬ: они меняются при установке на другой
    том, а не между редакциями. [Д: reloc.md §1, §4]

#### Шаг b. Побайтовое сравнение и классы слов

 1. Сравнить слова по индексу wa = 0..1023:
    diff = [wa : A[wa] != B2[wa]].
    [Д: Z0172-COMPARE.md, воспроизведение]
 2. Каждое diffs-слово отнести к одному из классов:

    DEL - запись удалена: значение A[wa] больше не
      встречается ни в одном из 1024 слов B2;
    SHFT - чистая релокация: A[wa] == B2[wa-k];
    EDIT - правка поля: A[wa] != B2[wa-k] (или
      A[wa] != B2[wa] при k=0), но тег/префикс
      сохраняется.

 3. DEL проверять только по всей зоне B2, а не по
    одной позиции: иначе удаление путается с релокацией.
    [Д: Z0172-COMPARE.md §2]

#### Шаг c. Поиск сдвига k по якорям LCS

 1. Найти равные слова-якоря в хвосте зоны и взять
    k = wb - wa, где A[wa] == B2[wb].
 2. Если k постоянен на всех якорях - одна вставка/
    удаление в начале. Если k кусочно-постоянен -
    записи переменной длины, вставок/удалений несколько.
    [Г: Z0172-COMPARE.md §2, §4]
 3. Проверить гипотезу k на всех словах хвоста:
    доля A[wa]==B2[wa-k] должна резко вырасти
    относительно доли совпадений при k=0.
    [Д: versions.md §6 для класса S]

#### Шаг d. Числовой разбор EDIT-дельта

 1. Вычесть пары A[wa] - B2[wa-k] и построить
    гистограмму дельт (восьм. число, знак, число слов,
    какая половина слова изменилась).
    [Д: Z0172-COMPARE.md §3]
 2. Разложить слово на 16 окт. цифр (0 - левая,
    старшая; 15 - правая, младшая):
    - цифры 13-15 = младшие 9 бит ПРАВОГО полуслова;
    - цифры 5-7 = младшие 9 бит ЛЕВОГО полуслова;
    - цифры 0-4 и 8-12 = тег/код/мода.
 3. Локализовать дельту по разрядам. Примеры:
    -0o43   -> цифры 13-15, бит 0-8   (адрес правый);
    -0o6    -> цифры 14-15, бит 0-5   (адрес правый);
    +0o1    -> цифра 15,    бит 0     (адрес правый);
    -0o600000000 -> цифра 7, бит 24-26 (адрес левый);
    +0o100000000 -> цифры 6-7,бит 24-27 (адрес левый).
    [Д: Z0172-COMPARE.md §3, разбор по разрядам]
 4. Классификация дельты:
    - постоянная дельта в полях адресов, теги
      стабильны и неизменны -> ПЕРЕНУМЕРАЦИЯ адресов;
    - произвольная дельта, но теги стабильны ->
      ПРАВКА ЗАПИСИ (корректировка адресов);
    - изменение тегов/кодов операций ->
      ПЕРЕКОДИРОВКА содержимого.
    [Г: Z0172-COMPARE.md §3, §7]

#### Шаг e. Вывод о смысле полей

 1. Поля, которые меняются между изданиями, - адреса
    или индексы. Поля, стабильные во всех EDIT, -
    семантические теги/коды. [Г]
 2. Сверить структуру с эталоном дескрипторов:
    [константная метка | указатель], читается как
    пара полукоманд; 0165.0367 `0220 0000 0300 2621`

 3. Если меняются только адресные поля, а коды 0220,
    2240, 0300, 0010 сохраняются - это таблица
    указателей/дескрипторов, чьи адреса перенумерованы.

#### 5.3.3 Как цитировать аналог

Формат одной строки вывода:
  `модуль.be:A-B (данные); модуль.be:C-D (читатель)`
  [Д] - сам факт; [Г] - то, что мы назвали аналогом.

Правила:
 - источник - re-dispak как поведение/структура, код
   не копируется; фиксировать module:line;
 - если совпала только упаковка полей, но нет
   индексного читателя - писать "структурный аналог";
 - если совпала только роль (dispatch, код->объект),
   но нет 4-полевой упаковки - "функциональный аналог"
   и помечать звездочкой, как в
   NUMERIC-ARRAYS-B1.md:196;
 - одиночная константа (diski.be:70) и рабочая ячейка
   (slojka.be:1260) НЕ таблицы и аналогом таблицы
   не считаются. [Д: Z0172-COMPARE.md §5]
