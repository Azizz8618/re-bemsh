## 2. Почему «метка в первом поле» здесь не работает

### 2.1 Факт из эталона

    dis-forced/Z0137.asm:587   16 31 01036  пв A01036(М16)
    dis-forced/Z0137.asm:1089  1036: 00 007 0000  A01036 вчаб

Поле адреса команды = `01036₈`. Это ровно индекс слова в зоне (0-based):
`1036₈ == 01036₈`. То есть скомпилированная программа использует
**зону-относительные (0-based) адреса** для внутренних процедур.
База модуля при этом `010000₈` ( prescribing оператора), и первое слово
модуля в листинге стоит по адресу `010000₈`:

    listing.out:318  ... 10000 00 000 0000 ... ЗП  , INIT_ZERO
    listing.out:320  ... 10001 ... ЗП
    listing.out:322  ... 10002 ... I3 ЗП   (до правки)
    listing.out:1421 ... 11036 ... I1036 ВЧАБ (до правки)

Следовательно, метка в первом поле на слове с индексом 1036 всегда даёт
`010000₈ + 1036₈ = 011036₈`, а не `01036₈`. Это не баг реконструкции,
а разница в соглашении об адресах между эталоном и базой модуля.

### 2.2 Опыт 1: `СТАРТ '0'` (провален, отменён)

Замена `СТАРТ '10000'` → `СТАРТ '0'` и ссылки `ПВ I1036(М16)`:

    HAM=00001                 <- ассемблер зажал базу 0 в 1
    I1036 -> адрес 01037 (вместо 01036)
    ЧИCЛO OШИБOK=0001. MAKC CEPЬEЗH=4.
    RESULT: FAIL

`СТАРТ '0'` не даёт нулевую базу: `HAM=00001`, первое слово по адресу
`00001₈`, поэтому любая метка в первом поле на слове 1036 даёт минимум
`1 + 1036 = 01037₈`. Адрес `01036₈` недостижим для такой метки при любой
допустимой базе (0 зажимается в 1, база ≥ 1 даёт ещё больше).
Опыт немедленно отменён (файл восстановлен из копии).

### 2.3 Опыт 2: полное имя `A01036` в первом поле (провален, отменён)

    A01036 ВЧАБ              ; метка на слове 1036
    ПВ A01036(М16)           ; ссылка

    WORDS: всего=1024 совпало=1023 различий=1
    RESULT: FAIL
    listing.out:894  16 31 11036 ... ПВ A01036(M16)
    listing.out:1421 11036 ... A01036 ВЧАБ
    таблица символов: A01036 11036

Имя метки не влияет на её значение: значение определяется только
позицией слова и базой. `A01036` даёт ровно те же `011036₈`, что и
`I1036`. Опыт немедленно отменён.

### 2.4 Опыт 3 (принят): абсолютный `ЭКВ`-литерал

В сохранённом файле уже были заготовки, неактивированные:

    bemsh/MBE-Z0137.be:476 (до правки)  * SUB_I_1036 ЭКВ '1036'
    bemsh/MBE-Z0137.be:515 (до правки)  * INIT_I_3 ЭКВ '3'

Они активированы под короткими именами `I1036` / `I3` (≤6 символов,
как требует транслятор). `ЭКВ` подставляет литерал при трансляции,
не создаёт перемещаемой связи и не зависит от базы модуля:

    I1036 = '1036' -> поле адреса 01036  (совпало с эталоном)
    I3    = '3'    -> поле адреса 00003  (совпало с эталоном)

Результат: 1024/1024, 0 различий. `RESULT: PASS`.

### 2.5 Про `ВХОДН` (подход 4)

`ВХОДН` объявляет entry point, чьё значение равно адресу метки, и не
меняет это значение (docs/VHODN-VNESHN-SYNTAX.md §1.3, §2). Если метка
`I1036` остаётся меткой первого поля, её значение `011036₈`; `ВХОДН`
не может превратить его в `01036₈`. Поэтому подход 4 не даёт не даёт
решения и не применялся. Единственный механизм, задающий абсолютное
значение символа, здесь — `ЭКВ` с литералом.

## 3. Почему G-метки работают в ДИСПАК, а здесь нет

Доказательства (не гипотеза):

1. `re-dispak/apunkt.be:1`: `АПУНКТ СТАРТ '10000'` — база `010000₈`.
2. `re-dispak/apunkt.be:23`: `G10012 сч` — метка в первом поле.
3. `re-dispak/apunkt.be.lst:39`:
   `10012 00 010 0000 ... G10012 СЧ` — слово с меткой лежит по адресу
   `010012₈ = 010000₈ (база) + 012₈ (индекс)`.
4. `re-dispak/apunkt.be.lst:374` (таблица символов): `G10012 10012` —
   значение метки равно `010012₈`, то есть **база + индекс**, и ровно
   такое же значение стоит в поле адреса ссылок
   (`apunkt.be.lst:32`: `ПЕ G10012`, значение `10012`).
5. `apunkt.be:17`: `пе G10012` — ссылка пишется напрямую, без `-З`,
   потому что соглашение эталона ДИСПАК совпадает с соглашением
   ассемблера: адрес = база + индекс.

В зоне 0137 другое соглашение: эталонное поле адреса для процедуры на
слове 1036 равно `01036₈` = индекс, **без базы** (п. 2.1). Поэтому
механизм `G`-меток (имя = база + индекс) здесь даёт `011036₈` — на
`010000₈` больше эталона, что и показано в опыте 2.

Иными словами: ДИСПАК-модуль `АПУНКТ` загружается по базе `010000₈`,
и его объектный код содержит адреса с этой базой; зона 0137 в эталоне
имеет 0-based адреса внутренних процедур, а реконструкция обязана писать
`СТАРТ '10000'` по указанию оператора. Разница соглашений, а не
синтаксиса меток, и есть причина, почему `G`-метки там работают,
а метка первого поля здесь — нет.

Разница инструментов тоже существенна: `apunkt.be` компилируется
и компонуется как настоящий модуль ДИСПАК с символьной таблицей и
перемещением; зона 0137 проверяется побайтово скриптом
`tools/rebuild-zone.sh`, который сопоставляет слова листинга с эталоном
по базе из `СТАРТ` (`tools/rebuild-zone.sh:135-181`). `ЭКВ` не порождает
слов и не попадает в перемещения, поэтому он меняет только текст
источника, но не объектные слова — ровно то, что нужно.

## 4. Итог

Правка не изменяет ни одного байта эталона и устраняет последний
`З`-вычитаемый хак. Способ полностью соответствует существующему
стилю файла (286+ `ЭКВ`-литералов) и его же собственным заготовкам
`SUB_I_1036 ЭКВ '1036'` / `INIT_I_3 ЭКВ '3'`.
