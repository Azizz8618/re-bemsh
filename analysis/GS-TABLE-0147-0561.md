## 2. Почему это точно БЕМШ, а не "похожий код"

[ФАКТ] Формула байта БЕМШ (обратная к декодеру):

    ISO < 0x40  → байт = ISO + 0x20   (зона 0x40-0x5f)
    ISO >= 0x40 → байт = ISO + 0x60   (зона 0xa0-0xdf)

[ФАКТ] Для всех 31 кириллической буквы GOST 040-076
выполняется тождество:

    TAB[gost] = all_to_iso[gost].CONS + 0x60

где `all_to_iso` из `monitor80-re/tools/encoding.cpp:713`
(порт ядра Дубны), четвёртое поле `CONS to ISO` (сдвиг 16).
Проверка 31/31. Примеры (шестн.):

    А: CONS 41 ('A')  + 60 = a1   TAB= a1
    Б: CONS 62 ('b')  + 60 = c2   TAB= c2
    Г: CONS 67 ('g')  + 60 = c7   TAB= c7
    П: CONS 70 ('p')  + 60 = d0   TAB= d0
    Ю: CONS 60 ('`')  + 60 = c0   TAB= c0

[ФАКТ] Для цифр и знаков тождество то же с другой зоной:

    '0': ISO 30 + 20 = 50   TAB= 50
    '+': ISO 2b + 20 = 4b   TAB= 4b
    ' ': ISO 20 + 20 = 40   TAB= 40

[ФАКТ] Столбец "CONS to ISO" в `all_to_iso` и есть тот же
самый алфавит, который декодер БЕМШ получает
вычитанием 0x60.
Совпадение 31/31 не может быть случайностью.

[ФАКТ] Таблица байт в точности повторена в дампе ленты Дубны
`besm6-new/dubna/tapes/bemsh739.c:1723-1735` сразу за кодом
макроредактора (последовательность 50 51 52 ... a4 a6 a7).
Это второе независимое вхождение той же таблицы.

## 3. Проверка на 16 известных парах

[ФАКТ] Байтовое совпадение 16/16 (источник пар:
`analysis/GOST-BYTE-FORMULA.md` §1):

    GOST  байта  GOST  байта  GOST  байта
     20    a1      22    a2      23    c7
     25    a5      2c    ad      2e    af
     2f    d0      30    b0      34    c6
     36    c3      38    db      39    dd
     3a    d9      3c    dc      3d    c0
     3e    d1

[ФАКТ] Составные имена из §7 предыдущего анализа тоже
совпадают: ПРЕ → d0 b0 a5; ВО → a2 af;
ГАММА → c7 a1 ad ad a1; юяц → c0 d1 c3.

[ФАКТ] Декодер БЕМШ (`dump.c:304-318`) применяет к этим
байтам вычитание 0x60 и получает код "ISO", который
`print_iso_char` (`dump.c:248-262`) печатает через
`koi7_to_utf8`. Для 10 из 16 пар получается тот же
кириллический символ (Г, П, Ф, Ц, Ш, Щ, Ы, Э, Ю, Я).
Для 6 пар (А, В, Е,
М, О, Р) получается латинский омоглиф (A, B, E, M, O, P).
Это свойство самой кодировки БЕМШ, а не расхождение таблицы.

[ФАКТ] Слова 0o0550-0o0560 перед таблицей суть код

[ФАКТ] Байты a6 a7 a9 aa ac ae b1 b2 b3 b5 b6 b7 ba be
это "пропущенные" коды букв, завершающие ту же таблицу за
пределами 64 байт. Читаемый фрагмент `счмр 64` использует
только первые 64.

[ФАКТ] Сообщений или меток, называющих таблицу, в зоне нет.
В `analysis/xref.txt:29663` у 00553 стоит
`по A00557 ... BR`. Само `A00557` в

## 5. ФАКТ / ГИПОТЕЗА / НЕ ИЗВЕСТНО

ФАКТ:
  таблица = GOST-10859 → БЕМШ, 64 байта, 0o0561;
  декодер БЕМШ в besm6-legacy/besmtool/dump.c:304-318;
  имя "кодировка БЕМШ" в ChangeLog r314 (11.11.2009);
  зоны "ТЕКСТ В КОДИРОВКЕ БЕМШ" в rukava.be:2767,2769;
  TAB[g] = all_to_iso[g].CONS + 0x60 для 31/31 букв;
  байт = ISO+0x20 (0x40-0x5f) или ISO+0x60 (0xa0-0xdf);
  16/16 известных пар совпадают побайтово;
  та же таблица в besm6-new/dubna/tapes/bemsh739.c:1723;
  метки с именем таблицы не найдены.

ГИПОТЕЗА:
  таблица включена в макроредактор как готовая константа
  Дубненской ОС, а не написана специально для него.
  Основание: точное совпадение с all_to_iso и с дампом
  ленты Дубны. Прямого указания в исходниках МАКРО-БЕМШ нет.

НЕ ИЗВЕСТНО:
  почему БЕМШ использует омоглифы латиницы для части букв
  (А→A, Б→b, В→B и т. д.) и почему 3 кода GOST (020, 024,
  034 в восьм.) не имеют изображения в декодере;
  причина дубля 0x47 у GOST 032 и 033;
  судьба байт за пределами 64 (0573-0577), точная роль
  continuing-таблицы не установлена.
