# Три детали таблицы GOST-10859 → БЕМШ по 0147.0561

Дата: 22.11.2026. Write set: только настоящий файл.
Образы, листинги и существующие файлы не изменялись.
Коммитов и push не делалось.

## 0. Краткий ответ

(a) GOST 0o020, 0o024, 0o034 суть математические знаки
    (показатель степени, умножение, не равно), которых нет
    в 7-битном алфавите БЕМШ. В таблице стоят байты 0x71,
    0x6f, 0x6d из неиспользуемого зазора 0x60-0x9f;
    декодер печатает "`". Почему выбраны именно эти числа,
    НЕ ИЗВЕСТНО.

(b) 0x47 дублируется у GOST 0o032 и 0o033. Это левая и
    правая типографские кавычки U+2018 и U+2019. В БЕМШ
    есть только один апостроф ISO 0x27, обе сводятся к
    байту 0x47. ФАКТ, омоглифное схлопывание.

(c) Байты после смещения 64 (слова 0147.0573-0577) суть
    продолжение той же таблицы GOST → БЕМШ для кодов
    0100-0131. ФАКТ, подтверждён формулой и лентой Дубны.

## 2. (a) Три кода без изображения

### 2.1 Что это за коды

[ФАКТ] Имена из `besm6-legacy/dispak/gost10859.h`:

    GOST_LOWER_TEN       0020  /* e  */
    GOST_MULTIPLICATION  0024  /* x  */
    GOST_NOT_EQUAL_TO    0034  /* #  */

[ФАКТ] По `monitor80-re/tools/encoding.cpp:39-40` и
       `tools/text_decode_all.py:48-49`, это Unicode:

    0o020 → U+23E8  ⏨  знак десятичной экспоненты
    0o024 → U+00D7  ×  знак умножения
    0o034 → U+2260  ≠  не равно

[ФАКТ] U+23E8 реально используется как показатель степени
       в `besm6-new/dubna/e64.cpp:467`: `e64_putchar(
       GOST_LOWER_TEN)`, затем знак и две цифры. Знак
      есть в GOST-10859, но отсутствует в БЕМШ.

### 2.2 Почему декодер не печатает их

[ФАКТ] `besm6-legacy/besmtool/dump.c:304-318` (-b):

    case 0100 ... 0137:  print_iso_char(p[i] - 040);
    case 0240 ... 0337:  print_iso_char(p[i] - 0140);
    default:             putchar('`');

[ФАКТ] Два диапазона байт задают 7-битный алфавит:

    0x40-0x5f → ISO 0x20-0x3f (пробел, цифры, знаки)
    0xa0-0xdf → ISO 0x40-0x7f (латиница + кириллица)

[ФАКТ] Три байта таблицы лежат в зазоре 0x60-0x9f:

    GOST 0o020 → 0x71   не покрыт декодером → "`"
    GOST 0o024 → 0x6f   не покрыт декодером → "`"
    GOST 0o034 → 0x6d   не покрыт декодером → "`"

Это не ошибка чтения дампа: те же три байта есть в
`besm6-new/dubna/tapes/bemsh739.c:1723-1735`.

### 2.3 Что показывает проверка формулы

[ФАКТ] Для всех остальных 61 элемента первых 64 байт
       выполняется правило (ISO = 7-битный омоглиф из
       `gost_to_unicode_lat`, `encoding.cpp:51-64`):

    ISO <  0x40 → байт = ISO + 0x20
    ISO >= 0x40 → байт = ISO + 0x60

Проверка: 61/61. Три элемента выпадают, и только они.

[ФАКТ] Арифметическое тождество для трёх байт:

    0x71 = 0x51 + 0x20   (0x51 = ASCII 'Q')
    0x6f = 0x4f + 0x20   (0x4f = ASCII 'O')
    0x6d = 0x4d + 0x20   (0x4d = ASCII 'M')

То есть применён младший сдвиг +0x20 вместо старшего
+0x60. ГИПОТЕЗА: так помечены позиции без глифа, чтобы
байт гарантированно попал в зазор и декодер
напечатал "`".

[ФАКТ] `unicode_to_koi7` (`encoding.cpp:176-230`) даёт для
       этих символов другие коды: U+23E8 → 0x17,
       U+00D7 → 0x06, U+2260 → 0x18. К Q/O/M они
       отношения не имеют.

### 2.4 Граница знания

НЕ ИЗВЕСТНО, почему конкретно 0x71, 0x6f, 0x6d.
Прямого указания в исходниках МАКРО-БЕМШ, в ленте
Дубны и в `docs/TEXT-CONSTANTS*.md` не найдено.
Возможные объяснения (без доказательства): мусор от
первоначальной сборки таблицы, или номер позиции в
другом, несохранившемся алфавите. Не фиксируем.

## 3. (b) Дубль байта 0x47

[ФАКТ] Полный перечень повторов в первых 64 байтах
       (индексы восьмеричные):

    byte 47: 032, 033

Больше ни одного дубля нет.

[ФАКТ] Расшифровка двух позиций по `gost10859.h`:

    GOST_LEFT_QUOTATION   0032  U+2018  ‘
    GOST_RIGHT_QUOTATION  0033  U+2019  ’

[ФАКТ] `encoding.cpp:51-64` ставит обоим ISO 0x27
       (ASCII апостроф `'`, один на обе кавычки). Далее:

    0x27 + 0x20 = 0x47   обе позиции

[ФАКТ] dump.c:257-267 печатает ISO 0x27 как ASCII `'`.
       Различие открывающей и закрывающей кавычки
       теряется: это омоглифное схлопывание в БЕМШ,
       где один знак апострофа заменяет обе кавычки.
       Обратная таблица поэтому неоднозначна, прямая
       подстановка однозначна.

[ФАКТ] Пример из задания "латиница C против кириллицы С"
       к дублю 0x47 отношения не имеет: латинские буквы
       F..Z лежат за пределами 64 байт (см. §4), а
       GOST 0061 (С кириллическое) даёт 0xa3 и не
       совпадает ни с одним другим индексом первых 64.

## 4. (c) Байты после смещения 64

### 4.1 Что там лежит

[ФАКТ] Массив продолжается без разрыва. Индекс 64 = GOST
       0100. Побайтовое соответствие слов 0573-0577:

    слово  байты         GOST → знак
    0573   dc c0 d1 a4  0074 Э, 0075 Ю, 0076 Я, 0077 D
           a6 a7        0100 F, 0101 G
    0574   a9 aa ac ae  0102 I, 0103 J, 0104 L, 0105 N
           b1 b2        0106 Q, 0107 R
    0575   b3 b5 b6 b7  0110 S, 0111 U, 0112 V, 0113 W
           ba be        0114 Z, 0115 черта сверху
    0576   6c 6e 76 46  0116 ≤, 0117 ≥, 0120 ∨, 0121 ∧
           7e 7c        0122 ⊃, 0123 ~
    0577   7f 7d 45 44  0124 ÷, 0125 ≡, 0126 %, 0127 ◇
           77 4d        0130 |, 0131 ―

[ФАКТ] Для 14 символов GOST 0100-0115 (латинские буквы
       и черта сверху) формула ISO + 0x60 выполняется
       14/14: a6 a7 a9 aa ac ae b1 b2 b3 b5 b6 b7 ba be.

[ФАКТ] Далее формула работает для всех знаков, у
       которых есть омоглиф в БЕМШ:

    GOST 0126 % → 0x25 + 0x20 = 0x45   байт 0x45
    GOST 0132 _ → 0x5f + 0x60 = 0xbf   байт 0xbf
    GOST 0133 ! → 0x21 + 0x20 = 0x41   байт 0x41
    GOST 0134 " → 0x22 + 0x20 = 0x42   байт 0x42

Итого 18/18 проверенных байт продолжения совпали.

[ФАКТ] Для знаков без глифа (0116-0125, 0127, 0130,
       0131) таблица снова кладёт "сырые" ASCII-подобные
       байты: 6c 6e 76 46 7e 7c 7f 7d 44 77 4d.
       Это тот же механизм, что и в трёх аномалиях §2.

### 4.2 Кто это использует

[ФАКТ] Код макроредактора читает только 64 байта:
       `счмр 64` (`dis/MBE-Z0147-L1.asm:611`), затем
       `сч A00557+2(М14)` (:612). Продолжение этим
       конкретным путём не используется.

[ФАКТ] Та же последовательность байт, включая
       продолжение до 0601 и дальше, лежит в ленте
       Дубны `besm6-new/dubna/tapes/bemsh739.c:1723-
       1745`. Значит это скопированная константа Дубненской
       ОС, а не локальная добавка макроредактора.

[ФАКТ] Слова 0602-0607 после продолжения образуют
       отдельную таблицу из 6 слов: d0, c0, b0, a0, 90,
       80 (шаг -0x10). К GOST → БЕМШ отношения не имеют,
       в данные задания слова 0573-0577 не входят.

[ФАКТ] Поиск по `docs/TEXT-CONSTANTS.md` и
       `docs/TEXT-CONSTANTS-ALL.md` не дал записей для
       адресов 0147.0573-0577. Записи вида `0573.0611`
       в тех файлах относятся к зоне 0573, а не к слову
       0573 зоны 0147. Именованной метки у продолжения
       нет.

## 5. ФАКТ / ГИПОТЕЗА / НЕ ИЗВЕСТНО

ФАКТ:
  0o020 = ⏨ (U+23E8), 0o024 = × (U+00D7), 0o034 = ≠
    (U+2260); все три вне алфавита декодера dump.c;
  байты 0x71, 0x6f, 0x6d в зазоре 0x60-0x9f → "`";
  61/61 остальных элементов первых 64 байт следуют
    правилу ISO + 0x20 / ISO + 0x60;
  0x71 = 0x51+0x20, 0x6f = 0x4f+0x20, 0x6d = 0x4d+0x20;
  дубль 0x47: GOST 0o032 ‘ и 0o033 ’ → ISO 0x27;
  больше дублей в первых 64 байтах нет;
  слова 0573-0577 = GOST 0100-0131 той же таблицы;
  14/14 латинских букв 0100-0115 по формуле;
  18/18 байт продолжения проверено формулой;
  та же таблица с продолжением в bemsh739.c:1723;
  `счмр 64` читает только первые 64 байта.

ГИПОТЕЗА:
  три "сырых" байта в зазоре суть метка "нет глифа",
  выбранная так, чтобы декодер гарантированно выдал
  "`";
  конкретные значения 0x51, 0x4f, 0x4d, возможно,
  пришли из несохранившегося внутреннего алфавита.

НЕ ИЗВЕСТНО:
  причина выбора именно 0x71, 0x6f, 0x6d;
  причина, по которой БЕМШ не включил ⏨, × и ≠ в свой
  7-битный алфавит (документация по шрифту не найдена);
  роль отдельной таблицы 0602-0607 (вне заданных слов).
