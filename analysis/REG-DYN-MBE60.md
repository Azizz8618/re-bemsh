# Динамическая проверка М13, М14, М17 на задании mbe60

Живая трасса `dispak -tt` настоящего теста ДКС.
Дата: 22.11.2026. DELTA: только этот новый файл.
Продолжение `analysis/REG-DYN-MIN.md` (минимальное задание),
но с реальным исходником и большим числом повторов.

## 1. Цель

Проверить на live-трассе четыре утверждения
из `docs/REGISTERS.md`:

1. (a) ВЖМ (`vjm`) пишет адрес возврата в М13.
2. (b) Поздний возврат читает М13.
3. (c) М14 загружается параметром перед вызовом ВЖМ.
4. (d) М17 работает как link ВЖМ, индекс или контекст.

## 2. Методика и оговорка про печать

Рабочий каталог: `/tmp/.private/azizz/reg-trace-mbe60/`.
Образы 2048, 2053, 2099, 2248 скопированы из каталога
`/usr/local/share/besm6` (только чтение),
`BESM6_PATH` = копия. Эталон 2348 не копировался.

Блок печати `cu.c:417-444` стоит до `switch` в `cu.c:514`.
Поэтому `r[N]=value` в строке трассы есть значение
регистра **до** исполнения команды. ВЖМ в `cu.c:715`
делает `reg[i_reg] = nextpc`, где `nextpc = pc + 1`.
Свежий адрес возврата на строке `vjm` не виден, он
выводится из `pc+1` и проверяется поздним чтением `r[N]`.

Трасса (~2,5 млн команд) НЕ сохранялась: stderr шёл
потоково в фильтр, stdout (листинг) - в `listing.txt`.
Экономия места обязательна: `/tmp` - tmpfs,
около 420 МБ свободно.

## 6. Доказательства

### 6.1 (a)+(b): М13 как регистр связи ВЖМ

Вызовы `vjm ...(13)`. Поле `r[13]` = старое значение:

```
 70005: vjm 70067(13) acc=1200000000000000 r[13]=00000
 01352: vjm 1434(13)  acc=1200000000000000 r[13]=00000
 01405: vjm 1426(13)  acc=0002000000000000 r[13]=12000
 01424: vjm 1426(13)  acc=0000000000077667 r[13]=77667
 04507: vjm 77553(13) acc=0000000000000000 r[13]=04510
 04021: vjm 77114(13) acc=0000000000000260 r[13]=05236
```

Пары вызов -> возврат (`pc+1` совпадает с `r[13]`):

```
r13 CALL: 70005: vjm 70067(13) r[13]=00000
r13 RET : 70075: uj  (13)      r[13]=70006
r13 CALL: 01352: vjm 1434(13)  r[13]=00000
r13 RET : 01442: uj  (13)      r[13]=01353
r13 CALL: 01405: vjm 1426(13)  r[13]=12000
r13 RET : 01433: uj  (13)      r[13]=01406
r13 CALL: 01424: vjm 1426(13)  r[13]=77667
r13 RET : 01433: uj  (13)      r[13]=01425
```

| ВЖМ при pc | nextpc | чтение | r[13] | совпадение |
| --- | --- | --- | --- | --- |
| 70005 | 70006 | `70075: uj (13)` | 70006 | да |
| 01352 | 01353 | `01442: uj (13)` | 01353 | да |
| 01405 | 01406 | `01433: uj (13)` | 01406 | да |
| 01406 | 01407 | `01442: uj (13)` | 01407 | да |
| 01424 | 01425 | `01433: uj (13)` | 01425 | да |

| 05235 | 05236 | `77574: uj (13)` | 05236 | да |

Прямое динамическое доказательство (a) и (b).
Старые значения `r[13]` на строке `vjm` (00000, 12000,
77667, 04510, 05236) - следы прошлых вызовов:

### 6.2 (c): М14 параметр перед вызовом ВЖМ

`vjm` с link М14 не найдено (0 из 27867), хотя `uj (14)`
встречается 10683 раза. М14 наблюдается как
смещение/указатель:

```
 14167: utm -1(14)    acc=0000000031000270 r[14]=00270
 14171: vzm 14210(14) acc=0000000031000270 r[14]=00267
 14167: utm -1(14)    acc=0000000000041053 r[14]=00267
 14171: vzm 14210(14) acc=0000000000041053 r[14]=00266
 26151: uj  11(14)    acc=0000000000024333 r[14]=26150
 26434: uj  361(14)   acc=0000000000000000 r[14]=26150
```

`utm -1(14)` декрементирует М14, `vzm 14210(14)` пишет
слово по адресу из М14, `uj N(14)` - переход по таблице
с базой М14. Это динамическое подтверждение эталонной
роли "смещение/длина в буфере" (`VTM/UTM ...(М14)`).
Однако стадирование параметра именно перед `vjm` и
чтение его внутри callee в этом прогоне не пойманы:
исходный `ПВ RD16(М14)` (строки 76, 82, 96, 104,
117, 132, 134 в `mbe60_bemsh.txt`) не исполнялся,
так как задание подано через `ВВД$$$↑`, а не через
подпрограмму чтения с МЛ.

### 6.3 (d): М17 link ВЖМ и индекс

М17 тоже работает регистром связи ВЖМ,
с совпадающими возвратами (582 из 583):

```
r17 CALL: 70000: vjm 70076(17) r[17]=00001
r17 RET : 70103: uj  (17)      r[17]=70001
r17 CALL: 01345: vjm 1443(17)  r[17]=70001
r17 RET : 01450: uj  (17)      r[17]=01346
r17 CALL: 01354: vjm 1443(17)  r[17]=01346
r17 RET : 01450: uj  (17)      r[17]=01355
```

Пары: 70000->70001, 01345->01346, 01354->01355.
Все сходятся с `pc+1`. Индексная роль (обход таблицы):

```
 03750: vtm 65416(17) acc=6040000000065366 r[17]=00000
 03751: xta (17)      acc=6040000000065366 r[17]=65416
 03753: xta (17)      acc=0000000000000000 r[17]=65415
 03755: xta (17)      acc=0000000000000000 r[17]=65414
 03767: vtm (17)      acc=0000000000000000 r[17]=65366
 03715: vtm 65366(17) acc=4000000000000141 r[17]=00000
```

`r[17]` убывает 65416, 65415, 65414 в цикле

Признак "контекст задачи, 0(М17)" не наблюдался:
`xta (17)` и `vtm (17)` - обращение к памяти по адресу
из М17, не проверка флага.

## 8. Оговорки и открытые вопросы

1. Адреса трассы - 15-битные адреса памяти (`abpc`),
   не зоны диска. Зона памяти = адрес/1024. Дисковые
   зоны 0137-0177 в трассе не появляются
   (см. `tools/trace-translator.sh`).
2. `r[N]` - доисполненное (pre-state) значение. Адрес
   возврата на строке `vjm` не виден напрямую, он
   выводится из `pc+1` и подтверждается чтением. См. §2.
3. Диспетчер `01322` в прежней работе шёл через М16
   (`01220: vjm 1322(16)`, `r[16]=01130`). Здесь он
   тоже присутствует, но М13 и М17 дают свои пары.
4. Отрицательные поля `-1(14)`, `-37(17)` - 15-битные
   адреса (дополнение до 077777), не "отрицательные зоны".
5. Путь `ПВ RD16(М14)` из исходника не исполнялся:
   задание подано через `ВВД$$$↑`. Для проверки (c)
   нужен прогон с чтением исходника с МЛ или тест ДКС.
6. Полная трасса не сохранялась (экономия места).
   Сохранены только отфильтрованные файлы и листинг.
7. Контроль эталонного образа: md5
   `/usr/local/share/besm6/2348` в начале и в конце
   одинаков, `f8efceb2e89064d36daf451efea469dd`.
