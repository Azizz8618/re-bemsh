# LITERALS-ABSOLUTE-PROOF

Дата: 22.11.2026. Вопрос: литерал в ПВ/ПО/ПБ/ПЕ/И и в
ПИО/ПИНО есть абсолютный адрес или малое смещение от PC?

ВЕРДИКТ: АБСОЛЮТНЫЙ АДРЕС. Ни один путь декодирования
не прибавляет PC к полю адреса. PC сдвигается отдельно
(abpc/pc), а литерал идёт в JMP как есть. Индекс склады-
вается только у ПБ/ПО/ПЕ-форм (I_UJ), у ПВ (I_VJM) регистр
есть регистр связи и в цель НЕ входит.

Источники:
* dispak/dispak/cu.c, defs.h, optab.c, arith.c
* /tmp/.private/azizz/arap-dyn/B-explore.err (347.6 M,
  5 141 914 строк, потоковый разбор, без загрузки в память)
* dis/MBE-Z0147-L1.asm, bemsh/MBE-Z0147.be
* docs/DISBESM6-GUIDE.md, analysis/CALL-TRACE-RUNTIME.md

---

## 1. ФАКТ: статический разбор поля адреса

### 1.1 Декодирование (defs.h:127-145)

Laddr1 = (byte1<<8 | byte2) & 0177777   (15 бит, defs.h:127)
Laddr2 = (byte1<<8 | byte2) & 07777     (12 бит, defs.h:128)
Laddr  = Lstruct ? Laddr1 :
         Laddr2 | (Lexp ? 070000 : 0)   (defs.h:129-130)

Аналогично Raddr (defs.h:143-145). Бит расширения Lexp
просто ставит старшие биты 070000. Это НЕ знаковое
расширение малого смещения: адрес остаётся 15-битным
абсолютным (ADDR(x) = x & 077777, defs.h:257).

cu.c:55-61: unpack() кладёт это поле в ui.i_addr без
всякой привязки к PC.

### 1.2 PC сдвигается отдельно (cu.c:221-230)

221  abpc = pc;                  /* старый PC */
223  pc = ADDR(pc + right);      /* PC = PC + 0/1, вперёд */
228  addr = ADDR(ui.i_addr + reg[MODREG]);  /* если мода */
230  addr = ui.i_addr;        /* литерал как есть */

К `addr` НЕ прибавляется ни `pc`, ни `abpc`, ни `nextpc`.
Единственная добавка - reg[MODREG] (MODREG=020, то есть
М16, defs.h:62) в режиме «мода». Это индекс, а не PC.

### 1.3 Переходы (cu.c:595-596, 735-751, defs.h:39-47)

ПБ (uj, opcode 030, optab.c:94):
  595  case I_UJ:
  596    JMP(ADDR(addr + reg[ui.i_reg]));
  цель = литерал + индексный регистр. PC не участвует.

ПВ (vjm, opcode 031, optab.c:95):
  746  case I_VJM:
  747    reg[ui.i_reg] = nextpc;   /* регистр связи */
  748    reg[0] = 0;
  749    JMP(addr);                /* цель = литерал */
  литерал НЕ складывается ни с индексом, ни с PC.

ПИО / ПИНО (vzm 034, v1m 035, optab.c:98-99):
  735  case I_VZM:
  736    if (ui.i_opcode == 0115) {   /* 035 = ПИНО */
  737      if (reg[ui.i_reg]) JMP(addr);  /* reg != 0 */
  739    } else {                        /* 034 = ПИО */
  740      if (!reg[ui.i_reg]) JMP(addr); /* reg == 0 */
  743    }
  регистр здесь УСЛОВИЕ, а не смещение. Цель = литерал.

JMP (defs.h:39-47) делает только `pc = addr; right = 0;`.
Никакого `pc += ...` внутри нет.

### 1.4 Что значит '477' в .be

bemsh/MBE-Z0147.be:334:
  OUT477 (было 477) - A00477 OUT_PRINT; 0147:73; СР
Это ЭКВ-имя (символическое имя) для числового литерала
'477' восьмеричного. В листинге dis/MBE-Z0147-L1.asm:73:
  15 31 00477   пв  A00477(М15)
Поле = 00477, opcode 031 = ПВ, reg=15 (octal)=М15.
То есть '477' - это и есть абсолютный адрес 00477,
а не «смещение 477». Аналогично:
  .asm:395  13 31 00534  пв A00534(М13)  - адрес 00534
  .asm:626  11 31 00445  пв A00445(М11)  - адрес 00445

## 2. ФАКТ: динамика, трасса B-explore.err

Метод: cu.c:449-470 печатает `NNNNN: мнем операнд`;
следующая строка с адресом и есть фактическая цель
(JMP обнуляет right). `store`-строки в счёт не идут.

### 2.1 Пять CALL-сайтов в странице 0147 (PC < 02000)

1) 00400: vjm 437(15) r[15]=00005
   nextPC = 00437 = литерал 437; pc+1 = 00401
   reg=5 НЕ прибавлен: 437+5 = 444 != 00437
2) 01017: vjm 437(15) r[15]=00000
   nextPC = 00437 = литерал; pc+1 = 01020
3) 01034: vjm 476(15) r[15]=01030
   nextPC = 00476 = литерал; pc+1 = 01035
   reg=01030 (большой!) в цель не входит
4) 00674: vjm 736(15) r[15]=00463
   nextPC = 00736 = литерал; pc+1 = 00675
5) 00455: vjm 64002(15) r[15]=00401
   nextPC = 64002 = литерал; pc+1 = 00456

Ещё: 64143: vjm 64227(6) -> 64227 = литерал.

Все пять: nextPC == литерал, nextPC != pc+1.
Индексный регистр при ПВ в цель НЕ входит (он приёмник
адреса возврата, cu.c:747). Следовательно цель - самый
настоящий абсолютный адрес.

### 2.2 ПБ (uj): цель = литерал + индекс

6) 04013: uj 100            -> 00100 = литерал
7) 00110: uj 64000          -> 64000 = литерал
8) 64057: uj 62(15) r[15]=64000 -> 64062 = 62+64000
9) 64130: uj 122(15) r[15]=64000 -> 64122 = 122+64000

Здесь PC тоже не участвует: 64062 != 64060 (pc+1).
Индекс - абсолютное значение регистра, прибавляемое
к абсолютному литералу.

### 2.3 Сводка по всей трассе (522 839 переходов)

vjm (ПВ):   nextPC - литерал == 0 в 88 592 / 88 592
            случаев (100 %). Ни одного исключения.
uj  (ПБ):   nextPC - (литерал + регистр) == 0 в
            205 856 случаях (остальные - операнды вида
            `(16)` без литерала, где адрес берётся только
            из регистра). 1 случай с переполнением 0200000.

Это и есть доказательство: литерал - абсолютный адрес.

## 3. ФАКТ: ПИО и ПИНО (отдельный раздел)

### 3.1 Это переходы, но условные

Из cu.c:735-743 и optab.c:98-99:
  ПИО  (034, dispak vzm) - переход при reg == 0
  ПИНО (035, dispak v1m) - переход при reg != 0
Цель при переходе - тот же литерал `addr`, без PC.

### 3.2 Три конкретных случая из трассы

10) 64001: vzm 64015(16) r[16]=0
    nextPC = 64015 = литерал; pc+1 = 64002
11) 00702: vzm 706(11) r[11]=0
    nextPC = 00706 = литерал; pc+1 = 00703
12) 00707: vzm 674(12) r[12]=0
    nextPC = 00674 = литерал; pc+1 = 00710
13) 64503: v1m 64466(4) r[4]=23
    nextPC = 64466 = литерал; pc+1 = 64504

В случае 13 регистр=23 (ненулевой) - условие ПИНО
выполнено, но в цель НЕ прибавлен:
64466 + 23 = 64511 != 64466.
И здесь PC не прибавляется.

### 3.3 Статический пример '5505'(М13)

analysis/procedures-RESOLVED.md упоминает 0176:902-903;
реально это dis/MBE-Z0176-L1.asm:903:
  1524 13 35 05505   пино  '5505'(М13)
Поле = 05505 (4 восьмеричные цифры!), opcode 035 =
ПИНО, reg 13 (octal) = М13. По cu.c:735-737 цель -
05505 абсолютный адрес; М13 только проверяется на
ненулевость. «Малое смещение» 05505 быть не может:
это число ~2885, а не -3..+3.

### 3.4 ПИО36 (asn) - НЕ переход

optab.c:52: `asn` (опкод 036) реализован функцией asx
(arith.c:532) - арифметика с нормализацией порядков.
Трасса подтверждает:
  03661: asn 61      -> next 03661 (правая половина слова)
  03761: asn 117     -> next 03762 (pc+1)
  04005: asn 100(15) -> next 04006 (pc+1)
Распределение nextPC-pc: +1 в 104 790, 0 в 99 775
случаев. Ни одного «прыжка».

Адресное поле ПИО36 всё равно важно для меток: оно
используется как абсолютный адрес операнда для чтения
(LOAD(enreg, XADDR(addr + reg[i])), cu.c:456). Это
значит, что число в поле - адрес ячейки ОП (возможно
с индексом), а не смещение от PC. Метка должна ставиться
на этот адрес, даже если инструкция не передаёт управление.

## 4. ФАКТ: проверка контра-гипотезы (20 случайных ПВ)

Гипотеза: литерал - малое знаковое смещение (-3..+3),
прибавляемое к pc+1. Тогда nextPC-(pc+1) всегда был бы
в [-3,+3]. Результат (seed 20261122, 20 вызовов vjm):

    PC   oper     nextPC  pc+1  next-(pc+1)  lit
 01704 1731(2)    01731  01705         24  1731
 01345 1573(16)   01573  01346        225  1573
 01530 1345(15)   01345  01531       -164  1345
 01531 1541(15)   01541  01532          7  1541
 01514 1576(2)    01576  01515         61  1576
 00702  736(15)   00736  00703         33   736
 01637 1725(2)    01725  01640         65  1725
 01521 1602(2)    01602  01522         60  1602
 01520 1543(2)    01543  01521         22  1543
 01527 1533(15)   01533  01530          3  1533

(показаны 10 из 20; у всех 20 nextPC == литерал)

Только 1 из 20 разниц попала в [-3,+3] (01527: +3),
и то случайно: литерал 1533 просто оказался на 3 больше
pc+1. Цель всё равно равна литералу 1533, а не pc+1+3.
Гипотеза «малое смещение» ОПРОВЕРГНУТА.

Замечание про `-17(16)`: cu.c:452-456 печатает адреса
>= 077700 как `-(077777-addr+1)`. Это чисто типографский
приём для верхней области 15-битного адресного пространства
(см. docs/DISBESM6-GUIDE.md:46), а НЕ PC-относительное
смещение. defs.h:257 маскирует адрес в 077777.

## 5. ФАКТ / ГИПОТЕЗА / НЕ ИЗВЕСТНО

ФАКТ:
* Поле адреса декодируется в ui.i_addr (cu.c:57,61,
  defs.h:127-145) без PC; PC сдвигается отдельно
  (cu.c:221-230).
* ПВ/ПИО/ПИНО: цель = литерал; ПБ: цель = литерал +
  регистр. 88 592/88 592 ПВ попали точно в литерал.
* '477' в .be - это ЭКВ-имя абсолютного адреса 00477
  (bemsh/MBE-Z0147.be:334, dis/MBE-Z0147-L1.asm:73).
* ПИО36 (asn) не переход, но его поле - абсолютный
  адрес операнда (arith.c:532, cu.c:456).

ГИПОТЕЗА:
* Точные PCs из статического листинга (0040, 0304 и др.)
  не встречаются в B-explore.err: этот прогон загрузил
  образ иначе (код в 6xxxx и в странице 0147 с другими
  адресами). Поэтому в §2 использованы реальные CALL-сайты
  той же страницы 0147, найденные по PC в трассе.
  Статические сайты из .asm использованы в §1.4 и §3.3.

НЕ ИЗВЕСТНО:
* Не генерировался короткий прогон
  /tmp/.private/azizz/literal-proof/: трасса уже является
  доступной и исчерпывающей (347.6 M), а tmpfs /tmp на
  момент анализа заполнен (24 M свободно), что делает
  копирование томов 2048/2248 (по 31.5 M) невозможным.
  Это не ослабляет доказательство: статистика по 88 592
  переходам ПВ даёт 100 % совпадений.

## 6. Вывод для создания меток

Метки следует ставить на абсолютные адреса из поля:
  `A00477` = 00477, `A00534` = 00534,
  `'5505'(М13)` = 05505, и так далее.
Никакого «pc+1+небольшое смещение» не существует.
Для ПБ/ПО/ПЕ добавляйте индексный регистр к абсолютному
адресу; для ПВ/ПИО/ПИНО регистр в цель не входит.
Для ПИО36 (asn) метка нужна как метка ДАННЫХ по адресу
операнда, а не как цель перехода.
