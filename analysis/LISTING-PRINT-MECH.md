## 1. ПУТЬ ПЕЧАТИ: КТО ЗА ЧТО ОТВЕЧАЕТ

### 1.1 Гостевая программа против C-кода (ФАКТ)

Цепочка (порядок вызовов):
  1. vsinput.c кодирует карты задания в input queue.
  2. dispak.c вызывает vsinput(), затем input().
  3. input.c читает паспорт; e60() подаёт карты в память
     гостя.
  4. Транслятор БЭСМ-6 (ИПМ МАКРО-БЕМШ ВЕР.06/78) читает
     карты и выдаёт е64.
  5. extra.c print() исполняет е64 (не-нативный путь).
  6. cu.c вызывает dpout_decode() только для xnative.
  7. dpout.c dump() декодирует RLE-буфер АЦПУ и пишет
     в stdout через gost_write().

Ни в одном C-файле нет printf с "АДРЕС", "МЕТКА" или
"ОПЕРАЦИЯ". Шапка и штампы версий читаются как текст ГОСТ
из памяти гостя. C задаёт только механику вывода.

Примечание о номерах строк: в цитируемых отчётах указан
extra.c:1751 print(). В локальной копии
/home/azizz/dispak/dispak/extra.c диспетчер print()
находится в ст. 645-757, а e70 (обмен с диском) около
ст. 1719. Это разные ревизии одного файла; логика та же.

### 1.2 Что делает print() (ФАКТ)

Слово формата е64 (extra.c:680-685 лок. копии):
  format  0=текст ГОСТ, 1=команда, 2=восьмеричное,
          3=вещественное, 4=текст ITM;
  offset  позиция в буфере строки line[128];
  digits  число цифр для octal/real;
  final   признак конца строки (final & 8);
  width   ширина поля; repeat  повтор.

Функции печати (лок. копия):
  print_gost     :228   текст ГОСТ (format 0)
  print_command  :478   команда, две половинки (format 1)
  print_command1 :449   "рег код адрес" половинки
  print_octal    :405   восьмеричное, 5 цифр = АДРЕС
  print_real     :551   вещественное
  print_itm      :334   текст ITM
  lflush                вывод line в stdout
  dpout.c dump() :58    нативный RLE-буфер АЦПУ

print_octal сдвигает слово влево на 64-3*digits бит и
печатает digits октальных цифр. print_command собирает
две 24-битные половинки в 48-битное слово. Так в листинге
появляются колонки АДРЕС и КОМАНДА.

### 1.3 A00477 OUT_PRINT и сообщения АРАП (ФАКТ)

0147:0477-0512 (A00477 OUT_PRINT) единственная процедура
с явно описанным выводом (B147:301-307, GP:144-147):
  - читает счётчик D00717 и флаг D00722;
  - выделяет поле маской "сда 64-8";
  - пишет D00727 и буфер D01004;
  - возврат пб (М15) на 512.
CALL на A00477 идут из 0147:0040, :0052, :0534 и др.
Но ни в .be, ни в аннотациях нет указания, что она
печатает именно АДРЕС, МЕТКА или ОПЕРАНД. Это общий
диспетчер вывода ядра, не процедура конкретной колонки.

Зоны 0151/0152 это пул сообщений АРАП:
  0152.0002 ЗАПИСЬ АП...     статус
  0152.0151 НЕТ УПРАВЛ...    ошибка
  0152.0157 ОШИБКА СПРАВКИ   ошибка
  0151.0340 ОГЛАВЛЕНИЕ ТОМА  заголовок
CALL=0 у 0152, исполняемое слово одно (START). Значит
0152 не печатает колонки. Прямой ссылки OUT_PRINT к
текстам 0151/0152 нет (Z0151:252-253).

### 1.4 Почему атрибуция колонок НЕ ИЗВЕСТНО (ФАКТ)

  - Исходника транслятора на дисках нет.
  - disbesm6 не отслеживает значения регистров; "(Мn)"
    это поле команды, не доказанное значение.
  - xref.txt устарел, не имеет префиксов зон.
  - Шапка 0176.1743-1763 refs=0: прямых адресных
    ссылок из кода нет.
  - Единственная гипотеза "колонки печатает 0147"
    (Z0176:402) не проверяема без трассы вывода.
  - CALL-цели 0176 A01345/A01354 ложные (конк/конд).

Вывод: statically можно доказать только источник самого
текста шапки (0176) и существование общего OUT_PRINT,
но не соответствие "процедура = колонка".

### 1.5 Эхо карт: 014173 E64 (ФАКТ)

Эхо управляющих карт печатается отдельно от листинга:
  - 014410-014415 и 014173: *64 2(16) (Э64);
  - блок 074460: vjm 014113(15) тоже печатает строку.
Эхо стоит в начале stdout, сразу после штампов ИПМ
МАКРО-БЕМШ и АРАП ВАР.04/78. Латинские B/P/K вместо
В/Р/К ("BBД", "TPH", "KНЦ") это особенность печати
7-битным кодом, не другие карты. В листинге 0137 первые
строки именно такие (см. §4).

## 2. ТАБЛИЦА КОЛОНОК (ФАКТ)

Позиции 0-based, замерены по реальному листингу 0137
(строка 19). Уверенность относится к ИСТОЧНИКУ ЗНАЧЕНИЯ;
расположение текста в 0176 доказано для всех строк.

| колонка  | слово | поз. | источник          | увер   |
|----------|-------|------|-------------------|--------|
| ОШИБКИ   | 1743  | 0    | счётчик 0176.1016 | ГИП    |
| НПК      | 1744  | 9    | номер перфокарты  | ГИП    |
| СВОБ     | 1745  | 14   | поле размещения   | НЕ ИЗВ |
| ПЕРЕМ    | 1746  | 19   | ВНЕШН/СА, бит 21  | ФАКТ   |
| АДРЕС    | 1747  | 25   | база+индекс, СТАРТ| ФАКТ   |
| КОМАНДА  | 1750-51| 31   | 2 половинки слова | ФАКТ   |
| А ИСП    | 1752  | 42   | ПБ/ПЕ: база+индекс| ФАКТ   |
| N ГЕН    | 1753  | 48   | поток 0170        | ГИП    |
| N ИСХ    | 1754  | 54   | номер строки      | ГИП    |

  - N ГЕН / N ИСХ: гипотезы по тексту, не CALL-связь.

## 3. РАЗБОР ЛИСТИНГА В rebuild-zone.sh (ФАКТ)

Код: tools/rebuild-zone.sh:131-197 (второй heredoc).

  1. a = line[25:30]  поле АДРЕС, 5 октальных цифр.
     addr = int(a,8) если fullmatch \d{5}; пусто -> None;
     непустое не-октальное -> 'bad' (строка пропускается).
  2. rest = line[31:].lstrip()  всё правее колонки 31.
  3. RE_WORD: 16 октальных цифр в начале rest, слово КОНД.
     Если addr задан: words[addr] = int(word,8),
     pending сбрасывается.
  4. RE_CMD: reg из 2 цифр, op из 2-3, af из 4-5,
     в начале rest. reg, op, af дают half = (reg<<20)
       | (op << (15 если af из 5 цифр, иначе 12)) | af;
     первая половинка: words[addr] = half << 24,
       pending = addr;
     вторая (addr пусто): words[pending] |= half.
  5. BASE: из СТАРТ в .be ('10000' -> 0o10000, пусто -> 1).
     Берём базу с бо́льшим числом совпадений с gold;
     при равенстве берём 1 (1-based). Слово i ищется по
     адресу BASE+i. Итог для 0137: NW=1024, PASS.

### 3.1 Колонка ПЕРЕМ / TRACE и её влияние на разбор

[ФАКТ] ПЕРЕМ занимает фиксированное поле [0:25], левее
       АДРЕС. Отметка `+N` (например `008+ 0016-00001`)
       остаётся в этом поле И НЕ сдвигает АДРЕС с [25:30].
       Разбор по фиксированному срезу устойчив. Но наивный
       поиск "первых 5 цифр" ломается: в `0016-00001`
       число 00001 лежит на позиции 19, и его можно
       принять за адрес.
[ФАКТ] Строки трассировки dispak -t вида `*** E64 ...`
       печатаются отдельными строками ДО данных. У них
       нет адреса в [25:30], они попадают в мусорные и не
       влияют на слова.
[ГИПОТЕЗА] Если trace-колонка будет вставлена внутрь самой
       строки, все позиции сдвинутся и жёсткий срез [25:30]
       перестанет быть адресом. В листинге 0137 такой
       колонки в строках нет.

### 3.2 Известные ловушки

  1. Омоглифы. Печать 7-битным кодом даёт латинские
     C/P/K/B/M/E/H/T/X/Y вместо кириллических. Заголовок
     "OШИБKИ ... AДPEC ... METKA", штамп
     "ИПM MAKPO-БEMШ BEP.06/78". Регексы по кириллице
     без нормализации не находят шапку и счётчик ошибок.
  2. BOM. Файл начинается с \ufeff; первая строка не
     распознаётся, если BOM не снят.
  3. Разделённые половинки. af из 4 цифр даёт сдвиг op 12,
     из 5 цифр сдвиг 15. Перепутывание даёт мусорное слово.
  4. 1-based против базы. АДРЕС это база+индекс. Выбор
     BASE отдельная задача; в 0137 BASE совпал со START
     и дал 1024/1024.
  5. Повторяющаяся шапка. На каждой странице шапка
     повторяется; её строки идут в non_address_lines.
