  макрос без имени, шапка ЭКВИВ 16 параметров;
  63: ∧А(1) ЭКВ ∧А(2)   - связать первый со вторым;
  64: АIF (∧Б ЕQ '').ВСЕ - если второй пуст, выход;

Итого: правый сдвиг списка до пустого ∧Б. Каждый шаг
связывает пару (∧А(1), ∧А(2)). Это "-" по списку, а не
вычисление арифметического выражения.

ЭКВИВ пар (строки 78-84): макрос `М`, 4 строки задают
29 пар вида (М1,1) ... (М35,29). Числа 1..29 - явные

## 3. РЕЗУЛЬТАТ: подстановка ∧-параметра в ЭКВ

Тот же макрос вызывался с разными &a. Значение символа
E1 читалось из таблицы *MET* листинга (строка `E1 ...`).

  &a    E1 (*MET*)  расчёт = 0o103 + 48 - &a.
   0     00163       000163
   1     00162       000162
   5     00156       000156
  10     00151       000151
  48     00103       000103

ФАКТ: все 5 значений совпали с формулой.
  '103' читается как ВОСЬМЕРИЧНАЯ константа 103 (67d);
  48 - десятичное; &a подставляется как число.
ФАКТ: тип символа в *MET* - `A` (арифметический):
  строка 37 P5.listing.out:
  `E1     00156 A  000000 00000 ...`

ФАКТ: макрос без машинной операции не порождает
машинных слов:
  при теле только из ЭКВ листинг печатает
  `OПEPAЦИИ HET` (макрос не дал машинных слов).
  С машинной операцией `уиа &a` ошибок 0.

## 4. ТРАССА: где рождается вычисленное значение

Файл P5.trace.txt. Ниже - точные номера строк.

4.1 Операнды в памяти (ФАКТ):
  953052: 03573: xta 2002 (=0000000000100103)
          -> константа '103' с тегом 0010;
  953053: 03573: aox 2003 (=0000000000100060)
          -> 0060o = 48d;
  953054: 03574: aox 2004 (=0000000000100005)
          -> подставленный &a = 5.

4.2 Аккумулятор (ФАКТ):
  953068: 03610: aax 3724
          (=0000000000077777)
          acc=6400000000000156
  -> младшие 16 бит acc = 0156o = 110d = 103+48-5.
  953069: 03610: atx 2001  acc=0000000000000156
  953070: 02001: store 0000000000000156
  -> вычисленное значение записано в ячейку 02001.

4.3 Появление в слове листинга (ФАКТ):
  953083: 04146: aox 2001 (=0000000000000156)
  953084: 04147: atx (7)  acc=0001600000000156
          r[7]=73266
  953085: 73266: store 0001600000000156
  953089: 04151: atx (7)  acc=0001600000100156
  953090: 73266: store 0001600000100156
  -> из 0156 построена запись таблицы *MET*;
     та же запись видна в P5.listing.out:37 как
     `E1 00156 A`.

  Трасса 953052-953090 - один непрерывный фрагмент:
  загрузка операндов -> арифметика -> 02001 -> 73266
  -> строка *MET* листинга.

4.4 Отрицательный результат (ФАКТ):
  В P5.listing.out НЕТ 16-восьмеричных слов объекта
  (DTRAN: MBE60 IS ABSENT). В FULL-прогоне (полная
  программа из 276 строк) 38 объектных слов, но ни
  одно не содержит `0156`. То есть в этих опытах
  вычисленное значение попадает в *MET*, а не в слово
  объектного модуля.

## 5. СВЯЗЬ С ТАБЛИЦЕЙ ГС (счётчик 01201)

Контролируемые наборы (полная программа, macro
НЕ вызывается, 0 ошибок макросов):

  N0: без макросов        ГС=001332
  N1: макрос ПРЕ, без ЭКВ ГС=001334 (+2)
  N2: тот же макрос + ЭКВ  ГС=001334 (+2)
  N3: макрос только с ЭКВ  ГС=001334 (+2)

ФАКТ: добавление строки ЭКВ в тело макроса НЕ меняет
счётчик ГС (N1 == N2 == N3 == 001334).
ФАКТ: гранулярность +2 на зарегистрированный макрос
совпадает с MACRO-TABLE-FORMAT-VERIFIED.md §4.1.

ФАКТ (идентичность 01201):
  в P5.trace.txt последняя запись в 01201:
  911474: 01201: store 0000000000001124
  что равно `001124-KOЛИЧ ЯЧ ГC` из P5.listing.out.
  Это подтверждает GS-TABLE-BITS.md §2.1: 01201 -
  физический адрес печатного счётчика ГС.

НЕ ИЗВЕСТНО (честно): биты ячеек ГС так и не
наблюдались; по GS-TABLE-BITS.md прямой съём не удался.
Эксперимент N1/N2 меряет только счётчик, не таблицу.
Вывод "ЭКВ не выделяет ячейку ГС" строгий только для
счётчика: счётчик не растёт. Может существовать
внутренняя таблица символов *MET*, её рост отдельно
не измерен.

## 6. ФАКТ / ГИПОТЕЗА / НЕ ИЗВЕСТНО

ФАКТ:
 - 9 командных вхождений ЭКВ/ЭКВИВ в macros.be
   (3 ЭКВ + 6 ЭКВИВ), плюс 1 комментарий.
 - ЭКВИВ в macros.be - это сдвиг списка ∧-параметров
   с рекурсией (62-65) и вектор явных пар (80-83).
 - ЭКВ '103'+48-&a вычисляется как 0o103+48-&a.
 - подстановка &a = 5 видна как операнд 02004=...0005
   на строке 953054 трассы.
 - результат 0156 виден в acc (953068), в 02001
   (953070) и в записи *MET* 73266 (953085/953090).
 - в *MET* листинга значение печатается `E1 00156 A`.
 - ЭКВ само по себе не порождает машинное слово.
 - счётчик ГС (01201) от добавления ЭКВ не растёт.

ГИПОТЕЗА:
 - тег `0010` в слове 02002/02003/02004 означает
   "арифметический операнд" (по аналогии с типом A
   в *MET*). Прямого описания тега нет.
 - арифметика идёт через field-коды 0010XXXX и
   нормализацию `ntr 3` (строка 953066). Это чтение
   трассы, а не дизассемблированная семантика.
 - ЭКВИВ векторного вида (80-83) строит те же записи
   *MET*, что и ЭКВ, но не проверено динамически.

НЕ ИЗВЕСТНО:
 - где физически лежит таблица *MET* в момент
   работы макромашины и какова её ёмкость;
 - почему N4 (SETA без значения) даёт ошибку, а
   ЭКВ с тем же &a - нет;
 - попадает ли значение ЭКВ в объектное слово при
   другой конфигурации задания (ЗОНМОД/ДЛИНА ПРОГ);
 - точная роль поля `.Д` в `Е∧N.Д ЭКВ ...` (116);
 - отличается ли поведение в B2 (0554/0570).
