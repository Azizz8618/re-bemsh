## 0. ЗАЧЕМ

Нужен повторно используемый инструмент, который читает
огромную трассу связывания по строкам и не грузит её в
память целиком. Отдельно он разбирает декодированный
каталог РВС (z0001.txt) и относит исполненные PC к
модулям по восьмеричным адресам загрузки НАЗ.

Источники формата: analysis/Z0144-RVS-LINK-TRACE.md
и tools/text_pool_probe.py (стиль CLI и --check).

## 1. КАК ЗАПУСКАТЬ

  python3 tools/rvs_trace.py TRACE [TRACE...]
  python3 tools/rvs_trace.py TRACE --catalog z0001.txt
  python3 tools/rvs_trace.py TRACE --format json
  python3 tools/rvs_trace.py TRACE --check
  cat TRACE | python3 tools/rvs_trace.py -

Ключи: --catalog FILE, --format json|text, --check,
--help. Коды выхода: 0 успех, 1 нарушение --check,
2 ошибка ввода или аргументов. Файлы только читаются,
'-' означает stdin.

## 2. ПРАВИЛА РАЗБОРА: ФАКТ

Строка трассы считается исполненной командой, только
если она начинается с 5 восьмеричных цифр, двоеточия
и мнемоники. Примеры мнемоник: atx, *70, a-x, vlm.

Строки `store` (5 или 6 цифр перед двоеточием) это
запись в память, а не PC. Строки `DD pc=... u=...
z=...` это события ввода вывода, а не PC. Строки
KCNT и E70at попадают в счётчик прочих.

Страница это PC >> 9, то есть три младших восьмеричных
знака отбрасываются. Страница печатается тремя цифрами
(071, 070). Адрес PC проверяется по диапазону
0..0177777.

Каталог читается по разделителю U+203E ('‾'), поэтому
он может быть одной длинной строкой. Поля МДЛ, НАЗ и
ЗОНГП разбираются без учёта регистра. Из полей МДЛ
берутся имя и 6-значный код зоны на ленте, из НАЗ
восьмеричный адрес загрузки, из ЗОНГП номер зоны и
число страниц. Диапазон модуля:

  [НАЗ, НАЗ + число_страниц * 0o1000)

Конец диапазона не включается. Значения НАЗ вида
НС24400 не являются восьмеричным адресом: такой
модуль остаётся в отчёте без диапазона и не получает
попаданий.

## 3. СХЕМА ВЫВОДА: ФАКТ

JSON (sort_keys=True) содержит ключи:

  sources          список входных файлов
  catalog          путь каталога или null
  lines_total      всего строк
  page_shift       всегда 9
  counts           счётчики (команды, store, DD,
                   прочие, разные distinct_*)
  pc_min, pc_max   границы исполненных PC
  pages            список {page, count}
  top_pcs          список {pc, mnemonic, count}
  modules          записи каталога + count,
                   first_line, last_line
                   (номера строк в исходном файле)
  dd               total, by_u, by_z, by_pair,
                   pc_min, pc_max
  stores           total, distinct_addrs, top
  unparsed_samples до 5 примеров неизвестных строк

При --check добавляется ключ check с полями ok,
checked, violations_total, truncated, violations.
Список нарушений ограничен 30 записями, полное число
даётся в violations_total. Все счётчики и гистограммы
в памяти ограничены числом различных PC, страниц и
адресов store.

Инварианты --check: нет отрицательных счётчиков, PC
попадает в 0..0177777, диапазоны модулей не
пересекаются. Атрибуция при пересечении берёт самый
узкий диапазон, затем порядок в каталоге.

## 5. СТАТУСЫ ВЫВОДОВ

[ФАКТ] Все числа раздела 4 получены потоковым прогоном
4 058 804 строк. Время около 11 с, память 14 МБ.

[ГИПОТЕЗА] Выбор самого узкого диапазона при
пересечении даёт правдоподобную атрибуцию PC (ГЕН для
071, ГЕНС для 070, КАЧКА для 072). Это эвристика
инструмента, а не доказанное соответствие модуля.

[ГИПОТЕЗА] Последнее число ЗОНГП (01..04) это число
1024-словных страниц модуля. Оно используется как
длина диапазона; источник поля явно это не подтверждает.

[НЕ ИЗВЕСТНО] Как по одному PC различить модули с
одинаковым НАЗ, если их диапазоны совпадают. Для этого
нужна информация о загрузке конкретного ЗОНГП в
конкретном прогоне.

[НЕ ИЗВЕСТНО] Смысл НАЗ=000001: адрес 1 или признак
перемещаемого модуля. Инструмент трактует его как
адрес 1 и помечает пересечения через --check.
