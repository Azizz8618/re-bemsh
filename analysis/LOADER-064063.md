# Загрузчик по адресу 064063: источник и личность

Дата: 22.11.2026. Write set: только этот файл.
Коммитов и push нет. Существующие файлы не менялись.
Опыты на копиях томов в `/tmp/.private/azizz/loader-064063/`
и на готовом прогоне `/tmp/.private/azizz/arap-dyn/`.

Статусы:
- [ФАКТ] прочитано в исходнике, трассе или дампе.
- [ГИПОТЕЗА] догадка без прямого свидетельства.
- [НЕ ИЗВЕСТНО] ответа в полученных данных нет.

Восьмеричные адреса пишем как `014000`, степень как `↑`.

## 0. Главный результат

[ФАКТ] Код `064000-064100` это НЕ исходник DISPAK и не
модуль `dmlmb`. Это начальный загрузчик МОНИТОР-80
(early loader), прочитанный с дорожки 7 МБ-20 в обменную
страницу `AIO = 064000₈` дескриптором `RLOAD` (N 61)
из модуля `monitor80-re/utility/boot.asm`.

[ФАКТ] Загрузчик использует Э60 (`e60()` в `input.c`) для
чтения 24-словных блоков из входного буфера и раскладывает
их по адресам памяти, в том числе в страницу 06
(1024 слова, `014000-017777`).

## 1. ФАКТ: трасса 064063-064100

Прогон: `job-B-sostav-orig.b6`, локальный билд
`dispak/build/dispak/dispak`, `dispak -b`, брейкпойнт
`b 64063`, `t 2`, `sn 50`. Файл `trace50.err`.

Точная последовательность (PC, мнемоника, операнд, слово,
аккумулятор, регистр):

[ФАКТ] База подпрограммы `r[15] = 064000` не меняется.

он готовит модификатор адреса `064060`.
`vtm 64060(16)` берёт из обменной страницы указатель,
куда Э60 положит очередной блок.

## 2. ФАКТ: что копирует загрузчик

[ФАКТ] В полной трассе `B-explore.err` три режима
вызова одной и той же подпрограммы `64076`/`64077`:

* `r[2]=01777` -> приём в `00400...` (страница 00);
* `r[2]=13777` -> приём в `12000...` (страница 05);
* `r[2]=15777` -> приём в `014000...` (страница 06).

[ФАКТ] Для страницы 06 записано ровно 1024 слова
( строка `r[2]=15777` встречается 1024 раза ).
Это полная страница `014000-017777`.

[ФАКТ] Один блок = 24 слова. В трассе первого вызова
`atx 76401(2) ... atx 76430(2)`: 24 адреса подряд.
Это совпадает с `e60()` (`input.c:110-156`):

    if (fread(ibw, sizeof(struct ibword), 24, ibuf) != 24)
    for (i = 0; i < 24; ++i)
        core[reg[016] + i] = ibw[i].w;

[ФАКТ] Значит загрузчик читает входной файл ПОСЛЕДОВАТЕЛЬНО
24-словными пачками и раскладывает их по адресам через
`atx` с индексом `r[2]` (база страницы) и `r[4]` (счётчик).

## 3. ФАКТ: откуда берётся сам код 064000

[ФАКТ] В `monitor80-re/utility/boot.asm` найдено:

    строка 3:  AIO:,EQU,64000B
    строка 30: *0061B:,LOG,0014 3200 0021 0007
               . read loader to exchange page
    строка 55: ,*70,*0061B-C
    строка 57: ,UJ,AIO

`AIO` = обменная страница `064000₈`. Дескриптор 0061
читает загрузчик с МБ-20, дорожка 7, в `064000`.

[ФАКТ] Прямое совпадение с трассой. В `dd.err` (этот же
прогон с `BESM6_DD_DEBUG=1`):

    DD pc=00107L r016=00061 u=21 z=0007 RD
       uil=14/0/3200 uir=21/0/7

Поля дескриптора совпадают с `boot.asm:30` побайтово.
Следующая команда трассы:

    00110: uj 64000      . переход в загрузчик

[ФАКТ] В `monitor80-re/utility/loadlibr.asm` есть имя

    RLOAD:,EQU,61B       . IW ЧТ.ЗАГРУЗЧИКА

Это тот же дескриптор 61. Если `LOADF` из
`permanent/loadf.asm` выполняет `*70,61B`, он тоже
поднимает загрузчик в обменную страницу.

[ФАКТ] Заголовок задания в `B-explore.out`:

    МОНИТОР-80 (3.7) 25.09.84, МС ДУБНА ИАЭ

То есть исполняющая система это МОНИТОР-80, не DISPAK.

## 4. ФАКТ: механизм DISPAK-only

[ФАКТ] `e60()` (`dispak/dispak/input.c:110-156`) это
эмуляция Э60 на стороне C. Он читает `~/.besm6/
input_queue/NNN` и кладёт слова в `core[reg[016]+i]`.
В `cflags` сбрасывается бит `C_UNPACKED`.

[ФАКТ] Буфер создаёт `vsinput()` (`vsinput.c:71-110`)
через `scan()` (`vsinput.c:152`), а пишет отдельные
слова функция `dump()` (`vsinput.c:772-818`):

    ibw.tag = tag; ibw.w.w_b[i] = w >> (5-i)*8;
    fwrite(&ibw, sizeof(struct ibword), 1, ibuf);

`dump()` вызывается с тегами `W_IADDR`, `W_CODE`,
`W_DATA`. Размер записи 8 байт, заголовок 112 байт.

[ФАКТ] Супервизор DISPAK грузится отдельно:
`dispak.c:468-487`, `sv_disk[]` (`dispak.c:82-86`),
том 2099, зоны `0100-0105`, адреса
`0100000-0112777`. Страница 06 туда не входит.

[ФАКТ] Значит DISPAK поставляет только МЕХАНИЗМ Э60,
а машинный код загрузчика ему не принадлежит.

## 5. ФАКТ: отрицательный поиск

Искались числовые и символические формы:

* `064063`, `64063`, `064000`, `AIO` во всех `.asm`,
  `.masm`, `.be`, `.lst`, `.txt`, `.md` каталогов
  `dispak/`, `re-dispak/`, `monitor80-re/`,
  `re-bemsh/`, `simh/BESM6/`, `Yandex.Disk/`;
* машинные слова загрузчика (восьмеричные байты)
  `331 000 101 352 000 000` на адресе `064063`,
  `320 223 314 011 000 000` на `064061`,
  `320 223 314 320 263 202` на `064066`;
* последовательность `utc 101(15)` / `utc 60(15)`
  (`15 22 00101`, `04 22 00000`) в листингах;
* те же 6 байт (`DB 00 41 EA 00 00`) во всех
  доступных образах томов и в `gold/`.

Результат: исходного текста подпрограммы по
`064063` НЕ найдено.

[ФАКТ] Ложное совпадение: `re-dispak/dmlmb.lst:156`
имеет метку `ВЫЗ` на `064063` (`ПИНО ВЗОМБ6(М2)`),
но машинное слово там `02 35 64055`, а в памяти
`331 000 101 352 000 000`. Это другой модуль,
в данном прогоне по `064000` он не загружен.
Совпадение адреса случайно.

[ФАКТ] В `re-bemsh` этот вопрос уже помечен как
открытый: `docs/FINAL-REPORT.md:410`,
`docs/MACRO-COMMANDS.md:245`,
`analysis/MACHINE-PAGE6-ZONE.md` §6.2.

## 6. ГИПОТЕЗА

Подпрограмма `064000-064100` это самостоятельный
модуль начального загрузчика МОНИТОР-80, поставляемый
в постоянной библиотеке (дорожка 7 МБ-20). Он не имеет
исходного файла в доступных репозиториях: `README.md`
`monitor80-re` прямо называет дизассемблирование
начального загрузчика невыполненной задачей.

Схема: BOOT -> дескриптор 61 -> Э70 чтение дорожки 7
-> `AIO=064000` -> `UJ,AIO` -> Э60 чтение 24 слов
-> `atx` с базой `r[2]` -> страница 06 готова.

## 7. НЕ ИЗВЕСТНО

1. Исходный текст (`.asm`/`.be`) самой подпрограммы
   `064000-064100`. Найден только BOOT-дескриптор,
   который её загружает.
2. Причина, по которой входной буфер содержит блоки
   именно для страниц 00, 05, 06 в таком порядке.
3. Точное назначение ячеек `064101` и `064060`,
   откуда берётся указатель `r[16]` и база `r[2]`.
