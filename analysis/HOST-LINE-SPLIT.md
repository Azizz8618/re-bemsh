# Кто делит строку на поля БЕМШ

Дата: 23.11.2026. Write set: только 3 новых файла.
Коммитов, push и правок существующих файлов НЕТ.
Адреса восьмеричные, степень ↑, тире нет, строки <= 60 кол.

## 0. ВЕРДИКТ

[ФАКТ] Хост НЕ делит исходную строку на поля.
Виртуальное считающее устройство dispak только
преобразует ввод в 48-битные слова и кладёт их
в input_queue. Разделение на МЕТКА / ОПЕРАЦИЯ /
ОПЕРАНД / КОММЕНТАРИЙ делает гостевый транслятор
(ИПМ МАКРО-БЕМШ), а не C-код эмулятора.

[ФАКТ] Фиксированной раскладки колонок хоста
(1-8 метка, 9-15 код и т.п.) НЕ существует.
Единственный номер колонки на хосте - физическая
сетка 12x80 в prettycard(), и она идёт только
в текст ошибки "ЗАМЯТИЕ".

[ФАКТ] Маркеры ВВД$$$ и КВЧ$$$ хостом не
интерпретируются. Это обычные символы в потоке
текстовых слов; их видит гостевый диспетчер.

[НЕ ИЗВЕСТНО] Точная процедура гостевого разбора
полей. В доступных трассах отдельного шага
разбиения нет, см. SOURCE-LINE-PARSER-EXP.md:46-57.

## 2. ЧТО ДЕЛАЕТ ЧТЕНИЕ КАРТ

A0/A1, vsinput.c:483-522
  itm = (ch == GOST_0): A0 кодирует в ITM через
  gost_to_itm[] (encoding.c:358-372), A1 пишет
  сырые байты GOST. Цикл 488-520 берёт ровно
  6 символов на слово, переводы строк пропускает
  (489-491). Пара _$ завершает текст (505-513).
  Ни колонок, ни полей: просто 6 символов в слово.

A3/A5, vsinput.c:523-599
  557: если строка имеет 80 символов и все они
  '.' или 'O' (is_prettycard, 121-130), идёт
  prettycard(). Это 12 строк по 80 отверстий.
  563-582: иначе читается punch.inX по 120 байт.
  583-594: обычный текст, 5 символов в слово,
  старший бит = parity(c) (587, parity в 112-119).

chad(), vsinput.c:643-662
  index = bit/40; 'O' даёт бит 1, '.' даёт 0.
  При чужом символе pncline = bit/80+1,
  pncsym = (bit%80)/8+1, текст "ЗАМЯТИЕ" (658).
  Это единственное место, где хост считает
  "строку карты" и "колонку" (группу из 8).

prettycard(), vsinput.c:665-684
  12*80 = 960 бит -> 24 слова по 40 бит.
  Разбиения на метку/код/операнд НЕТ.

## 3. ВВД$$$ ... КВЧ$$$

В колоде tests/bemsh-standalone/bemsh-standalone.b6
строки 16-27 идут после директивы a1. Хост кладёт
их в W_DATA пословно. В дампе очереди (deckA) это
видно как подряд:

  ВВД◇◇◇|...|КВЧ◇◇◇|...

GOST_DIAMOND = 0127 (gost10859.h:101) - это и есть
'$' в исходнике. Гостевой диспетчер читает эти
маркеры и начинает/кончает приём Fortran/БЕМШ
текста. Хост их не различает: в инструменте
маркеры дают host_action = 'none (packed as text
words)'.

AGENTS.md:322-347 показывает тот же блок:
  ВВД$$$ ; начало диспетчерского блока
  КВЧ$$$ ; конец вычислений
  ТРН$$$ ; конец трансляции
Это гостевая запись, не C-код.

## 4. N ИСХ / N ГЕН

AGENTS.md:274-275:
  N ГЕН - номер строки в генерируемом листинге;
  N ИСХ - номер строки в исходном файле.

Листинг делает гость. В bemsh-standalone/
output.txt шапка:

  ОШИБКИ НПК СВОБ ПЕРЕМ АДРЕС КОМАНДА А ИСП
  N ГЕН N ИСХ МЕТКА ОПЕРАЦИЯ ОПЕРАНД КОММЕНТАРИЙ

В конце две строки с N ГЕН 0010 и 0011 при
одном N ИСХ 0010 (*КОНЕЦ ЧАСТИ). Макрос дал
две генерируемые строки на одну исходную.
Поэтому гость и хранит оба номера.

Фактические колонки листинга (измерено в
DISPAK-LISTING-PAIRS.md:19-22):
  N ГЕН 48:54, N ИСХ 54:60, МЕТКА 60:67,
  ОПЕРАЦИЯ 67:76, ОПЕРАНД 76:86.
Это колонки ПЕЧАТИ гостя, не колонки ввода хоста.

Как гость узнаёт границы полей: он читает слово
за словом из core, собирает байты в текст и сам
решает, где метка, код и операнд. В трассах
SOURCE-LINE-PARSER-EXP.md:46-57 все четыре
уникальных токена лежат ОДНИМ байтовым рядом в
пуле 072000, без дескрипторов полей. Эхо листинга
печатает всю строку в КОММЕНТАРИЙ. То есть и у
гостя отдельного шага "разбить на поля" в трассе
не видно: поля - это способ печати, а не
самостоятельная структура в пуле.

KOI-7: таблица мнемоник лежит на гостевом диске
2348, зона 0137 (docs/SEMANTIC/Z0137.md:109-180).
Её читает besmtool --encoding=k. К хостовому
чтению карт она отношения не имеет.

Эталоны из build/dispak: 2048, 2053, 2099, 2248.
md5 эталонов до и после совпали (4/4):
  527d672e... 2048   8e827822... 2053
  137988d9... 2099   c11067b3... 2248

Колода A: bemsh-standalone.b6 как есть (табы).
Колода B: тот же файл, те же токены, но табы
заменены на 3-9 пробелов со сдвигом по колонкам.
Разница только в пробелах, см. diff в /var/tmp.

  dispak --path=/var/tmp/host-split/disks \
         deckA.b6 > runA.stdout

ФАКТ:
  очередь A  = 472 байт (112 паспорт + 45 слов)
  очередь B  = 592 байт (112 паспорт + 60 слов)
  W_DATA байт: 240 против 330

  215 байт в обеих колодах.
  => хост сохранил каждый пробел и не сделал

Листинги гостя побайтно равны:
  md5(runA.stdout) = md5(runB.stdout)

Замечание про -l: в dispak.c:176 это
--output-latin (латиница в выводе), НЕ ключ
листинга. Листинг печатает гость на stdout.

## 6. ИНСТРУМЕНТ

пакета vsinput.c:483-522 (и chad из 643-662).
CLI: --check, FILE..., --json. Проверяет, что

## 7. ИТОГ

ФАКТ
  Хост не делит строку на поля и не имеет
  фиксированной раскладки колонок. Он пакетит
  символы по 6 в слово (A0/A1), по 5 в слово
  с чётностью (A3/A5 текст) или по 40 бит
  на слово (пробивка). ВВД/КВЧ для него - текст.
  N ИСХ и N ГЕН - колонки гостевого листинга.

ГИПОТЕЗА
  Гость задаёт границы полей пробелами/табами и
  печатает их в колонки МЕТКА/ОПЕРАЦИЯ/ОПЕРАНД.
  Опыт это подтверждает (сдвиг колонок не меняет
  листинг), но исходник транслятора здесь не читан.

НЕ ИЗВЕСТНО
  Точная процедура гостевого разбора полей и то,
  существует ли она как отдельный шаг в трассе.
  См. SOURCE-LINE-PARSER-EXP.md:53-57.
