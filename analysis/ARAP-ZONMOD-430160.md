# ЗОНМОД430160: почему не 0233-0235, а одна зона 0160

Дата: 22.11.2026. Write set: только этот файл.
Коммитов и push нет. Ни один существующий файл
репозитория не менялся. Эталонные образы не менялись:
только read-only `view`, `search` и `dump`, плюс
прогоны на одноразовых копиях вне репозитория.

## 0. Статусы и оговорка

[ФАКТ] прочитано в исходнике, дампе, трассе или листинге
с адресом. [ГИПОТЕЗА] догадка без прямого свидетельства.
[НЕ ИЗВЕСТНО] ответа в полученных данных нет.
Восьмеричные адреса пишем как `0144.1774`, степень: `↑`.
Разделитель строк управляющих карт здесь заменён на `↑`,

## 1. Вопрос

ARAP-DIRECTIVES-DYN.md §7 и §11.3: задание J с картой
`ЗОНМОД430160  0001` дало сообщение `430160`, но
байтовое сравнение показало "физические зоны
0233, 0234, 0235". Для задания B с `ЗОНМОД430146`
дамп зоны 0146 сразу показал модуль СОСТАВ. Требуется
объяснить расхождение.

## 2. Короткий ответ [ФАКТ]

`0233-0235` не три записанные зоны. Это одна зона, чей
байтовый диапазон поделили на 6144 вместо 8256.

* логическая зона из операнда: `0160` (восьм.);
* дескриптор Э70 несёт ту же зону `00430160`;
* физический блок файла: `0164` = `0160 + 4` (oct);
* смещение `+4` это `ZONE_OFFSET` из diski.h:15.

Записан ровно один 8256-байтовый блок. Никакого
каталога, никакого `+0073` и никакой длины в 3 зоны
здесь нет.

## 3. Два разных размера "зоны"

[ФАКТ] `disk.h:28`:
```
#define ZONE_SIZE 6144
```
Это логическая зона БЭСМ-6, её и печатает `besmtool`.

[ФАКТ] `diski.h:21-23`:
```
typedef struct zone {
    uint64_t z_cwords[8];
    uint64_t z_data[1024];
} zone_t;
```
8 слов служебных + 1024 слова данных, по 8 байт:
`64 + 8192 = 8256` байт. Это физический блок файла.

[ФАКТ] `disk.c:557` (disk_writei2) и `disk.c:413`
(disk_readi2) ищут `lseek(fd, zone * sizeof(zone_t))`,
то есть шаг 8256, а не 6144.

[ФАКТ] `stat` образа 2248: 33024000 байт =
4000 блоков по 8256. 33024000 / 6144 = 5375, то есть
деление на 6144 даёт 5375 "зон", которых в файле
физически нет.

[ФАКТ] В `disk_readi2` (disk.c:405-409) и
`disk_writei2` (disk.c:552-554) для обычного режима
(`mode != DISK_MODE_PHYS`) стоит
```
zone += ZONE_OFFSET;   /* diski.h:15: 4 */
```

## 4. Прямые измерения по заданию J (зона 0160)

Одноразовая копия: `/tmp/.private/azizz/arap-dyn/2248`,
md5 `c40f95820aa4f23c7213d93e2a2ac104` (состояние после
J). Эталон: `/usr/local/share/besm6/2248`, md5
`c11067b35e2b85a51433e7d7b5efdd19`.

Команда сравнения (read-only):
```
python3 - <<'PY'
a=open('/tmp/.private/azizz/arap-dyn/2248','rb').read()
b=open('/usr/local/share/besm6/2248','rb').read()
for i in range(len(a)):
    if a[i]!=b[i]: ...
PY
```

[ФАКТ] Изменились байты `957696..965950`, всего 6248.
Группировка по 8256:
```
block dec 116  oct 0164  diffs 6248
```
Группировка тех же байт по 6144:
```
957696 // 6144 = 155 (oct 0233)
965950 // 6144 = 157 (oct 0235)
```
Вот откуда взялись "0233-0235": 8256-байтовый блок
накрывает три воображаемых 6144-байтовых интервала.

[ФАКТ] Проверка обратная. Приём `disk_readi2`: блок 116
(смещение `116*8256`), пропустить 64 байта `z_cwords`,
далее 1024 слова по 8 байт (little-endian), взять по 6
младших байт слова. Результат побайтово равен
`besmtool dump 2248 --start=0160 --length=1`:
```
0160.0000: 000000000001
0160.0001: b0b2afa74040
0160.0002: 000000000200
```
[ФАКТ] В дампе виден текст задания J:
`ПРИВЕТИК! ЭТО АВТОКОД БЕМШ.` (GOST-представление).

Команды:
```
BESM6_PATH=/tmp/.private/azizz/arap-dyn \
  besmtool dump 2248 --start=0160 --length=1 \
  --to-file=mod-z160.bin
BESM6_PATH=/tmp/.private/azizz/arap-dyn \
  besmtool view 2248 --start=0160 --length=1 \
  --encoding=g
```

## 5. Формула из исходника dispak

[ФАКТ] `extra.c:2774`:
```
ushort mask = getenv("BESM6_SMALL_DISKS") ? 01777 : 07777;
```
[ФАКТ] `extra.c:2785`, `2796`:
```
u = uir.i_opcode & 077;      /* номер диска */
zone = uir.i_addr & 07777;   /* зона из дескриптора */
```
[ФАКТ] `extra.c:3132-3135`, запись целой зоны:
```
r = disk_writei(dd->diskh,
        (zone + dd->offset) & mask,
        (char *)(core + addr), ..., DISK_MODE_QUIET);
```
[ФАКТ] `disk.c:554`, затем `disk.c:557`:
```
zone += ZONE_OFFSET;         /* +4 */
lseek(fd, zone * sizeof(zone_t));
```
Итого:
```
физ_блок = (зона_дескриптора + dd->offset + 4) mod 04000
```
[ФАКТ] В наших прогонах `dd->offset = 0`: измеренный
блок равен ровно `0160 + 4`. Э112 (задание смещения,
`extra.c:1907-1915`) в фильтре трассы не появился.

[ФАКТ] Дескриптор из трассы J
(ARAP-DIRECTIVES-DYN.md §5):
```
J @227 542 PC 07056 DESC=0000040000430160
```
Правое полуслово `00430160`: ЛУН 043, зона 0160.
Каталог в этом пути не участвует: число идёт из карты
в ячейку `01115`, оттуда в дескриптор, оттуда в Э70.

## 7. Поиск каталога на томе ленты 43 [ФАКТ]

Команды (эталон, только чтение):
```
BESM6_PATH=/usr/local/share/besm6 \
  besmtool search 2248 АРАП
BESM6_PATH=/usr/local/share/besm6 \
  besmtool search 2248 '*LIBRARY'
BESM6_PATH=/usr/local/share/besm6 \
  besmtool view 2248 --start=0 --length=1
```

* `search 2248 АРАП`: 0001.0045, 0011.0045,
  0115.0153, 0151.0361, 0152.0154, 0152.1164,
  3011.0005, 3030.0007 и др. Это штампы, тексты и
  сохранённый листинг, не таблица соответствий зон.
* `search 2248 '*LIBRARY'`: 0 попаданий.
* Зона 0 тома 2248 не читается как каталог Д-2048
  (нет шапки `*SFILE`, KOI-7 мусор). Ср.
  docs/IMAGES.md:31 и docs/catalog_zone0000.txt, где
  каталог с `*LIBRARY:` и зонами 0433-0437 описан для
  тома 2048, а не для 2248.
* Зона 0076 тома 2248 пуста (`UUUUUU`), зона 0433
  нечитаема.

[НЕ ИЗВЕСТНО] На томе 2248 не найдено каталога, который
отображал бы логическую зону в физическую. Причину
отсутствия каталога не определяли.

Поэтому гипотеза (b) "каталог логическая зона ->
физическая" не подтверждена: в пути Э70 виден прямой
номер зоны.

## 8. Проверка четырёх версий из задания

|версия |статус|основание          |
|-------|------|-------------------|
|(a) длина|НЕТ  |`ДЛИHA MOДЛ=00001`|
|(b) каталог|НЕТ |§7: каталога нет  |
|(c) +0073|НЕТ  |0160+0073 = 0253  |
|(d) адрес|ДА   |6144 вместо 8256  |

Отдельно [ФАКТ]: арифметика в (c) не сходится.
`0160` (112 dec) + `0073` (59 dec) = 171 dec =
`0253` (oct). Число `0073` в трассе и исходнике не
встречалось.

## 10. НЕ ИЗВЕСТНО

1. Точное слово `0234.0002 = 0000060000000022` из
   ARAP-DIRECTIVES-DYN.md §7 не воспроизвелось: в
   свежем прогоне J-эквивалента зона 0160 word 2 =
   `000000000200`. Совпадение одного слова с листингом
   (`01000 00 22`) перепроверено не было.
2. Артефакт `J-zone160.bin` в arap-dyn начинается с
   `aaaaaaaaaaaa / 555555555555` (заполнитель), это не
   дамп модуля. Его происхождение не установлено.
3. Что именно задаёт `dd->offset` для ЛУН 43 в других
   сценариях (Э112, Э63, карта `лент`): здесь он был 0.
4. Сколько зон займёт модуль длиннее одной зоны.
5. Почему запись видна только как Э70, без вызова из
   кода АРАП.
