## 1. Метод

### 1.1 Почему трасса решает вопрос

`analysis/CALL-TARGETS-RAM.md` §9 и `RAM-SNAPSHOT-MAP.md` §5
останавливались на косвенном признаке: «страница занята зоной»
не доказывает, что CALL туда идёт. Прямое доказательство даёт
последовательность PC. В `dispak/dispak/cu.c:383`:

```c
fprintf(stderr, "%05o: %-4s", abpc, op.o_name);
```

при `trace >= 2`, то есть `-tt`. Следующая строка с адресом и
есть фактический переход. Строки `store` печатаются с отступом
и в последовательность адресов команд не входят.

Коды `dispak` (`optab.c`) ↔ русские мнемоники (`disbesm6.c:117-124`):

| dispak | код | рус. | сколько | совпало с операндом |
|---|---|---|---:|---:|
| `vjm` | 031 | ПВ | 9526 | 9526 (100 %) |
| `v1m` | 035 | ПИНО | 11921 | 11292 (94,7 %) |
| `uj`  | 030 | ПБ | 43267 | 16839 (38,9 %) |
| `vzm` | 034 | ПИО | 6259 | 1693 (27,0 %) |
| `asn` | 036 | ПИО36 | 40364 | 0 (не переход) |

`vjm` — безусловный ПВ: `reg[i]=nextpc; JMP(addr)`
(`cu.c:677-681`), поэтому его операнд **всегда** равен следующему
адресу. Это и есть искомый переход.

### 1.2 Защита и входные данные

`tools/call_trace.sh` отказывается с exit 3, если `BESM6_PATH`
указывает на `/usr/local/share`, `~/.besm6`, `EC5061*` или
любой путь, отличный от `$WORK=/tmp/.private/azizz/call-trace/`.
Тома 2048, 2053, 2099, 2248 каждый раз заново копируются из
эталона: `dispak` записывает результат в подставной том 2248,
и без обновления копии второй прогон отличался бы от первого.
Задание — дословно каркас из `tools/ram_snapshot.sh` (режим
`0-0`, исходник `ТЕСТ СТАРТ 1 / Е / М / зп '70000' / ФИНИШ`).

### 1.3 Привязка адреса к зоне

`abpc` — 15 бит, адрес физический. Страница = `адрес / 02000₈`.
Соответствие страница → дисковая зона взято из 8 снимков ОП
(`analysis/RAM-SNAPSHOT-MAP.md`, `map-all.txt`):

```
00=0147 01=0154 02=0155 03=0156 12=0161 13=0162
34=0150 36=0153 (0151 в фазе загрузки)
37=0157 (0152 в фазе загрузки) 06,16,24 - пустые
```

Парсер `SnapshotMap` читает `map-all.txt` напрямую, поэтому
атрибуция не «придумана», а взята из побайтовой сверки снимков.

## 5. Вердикт

**Большие числовые операнды PROGRAM 2 НЕ являются адресами
резидентного кода Monitor-80.** Прямая трасса показывает:

1. исполняемые ПВ всегда идут по своему операнду (9526/9526);
2. все эти адреса лежат в страницах, которые 8 снимков ОП
   однозначно относят к зонам транслятора; страниц без зоны
   среди целей ПВ нет;
3. из шести «топ-целей» только `02070` и `77316` реально
   являются переходами; `34562`, `07417`, `51670` не
   исполнялись, `04114` — не цель CALL;
4. стало быть, гипотеза `CALL-TARGETS-RAM.md` §7 о «мониторных
   сервисах 07417/77316 как лидерах по входам» опровергается
   динамикой для этого задания: `07417` не вызывается вовсе,
   а `77316` ведёт в зону 0157/0152.

Оговорка: это только для данного минимального задания `0-0`.
Другая фаза/оверлей может загрузить на те же страницы другие
зоны; трасса этого прогона такой возможности не исключает.

## 6. Честные ограничения

1. `dispak` печатает адрес **слова**, а не полукоманды: левая и
   правая команды одного слова дают одинаковый `abpc`.
2. Мнемоника берётся из внутреннего кэша команд `uicore`
   (`defs.h:189`), который в установленном бинарнике недоступен
   (хуки `BESM6_CORE_ON_PC`/`BESM6_DD_DEBUG` в `strings`
   отсутствуют). Поэтому L1-слово по физическому адресу source
   часто помечено `конд` и расходится с исполненной мнемоникой.
   Вывод опирается именно на PC-последовательность, она не зависит
   от этого расхождения.
3. Имена `УППСЛУ`/`ДЛЯСВЯ` взяты из внешних листингов
   re-dispak; это логические адреса, побайтово с физическими
   страницами не сверенные (`AGENTS.md` §3). Здесь они не
   использовались как доказательство.
4. 8 снимков — дискретные точки; между ними возможны оверлеи.
   Атрибуция «зона 0157/0152» значит «на этой странице в снимках
   лежит эта зона», а не «никакой другой код там не бывает».
